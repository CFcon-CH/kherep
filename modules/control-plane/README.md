# Kherep Control Plane

A Cloudflare Worker that Kherep nodes connect to over an outbound WebSocket, plus the `kherep-node` daemon and CLI that runs on each node. It provides:

- **Nodes:** enrollment, node identity, registration, liveness and a registry of each node's runtimes and sessions. The operator API dispatches only three read-only commands (`node.status`, `runtime.list`, `session.list`); nothing runs arbitrary commands on a node (see [Commands](#commands)).
- **Messaging between agent sessions:** Claude Code and Codex sessions on any node list each other, send, read and reply. The receiving node's policy decides which senders it accepts, and delivery hooks hand messages to the session (see [Session messaging](#session-messaging) and [Codex sessions](#codex-sessions)).
- **Wake:** on by default with an explicit opt-out in `policy.json` (issue #390); wake supports eligible Claude Code sessions and Codex task sessions. Authorized interactive Codex original owners get CP hints and, with `wake.nativeQueue` opted in (off by default, issue #429), a native Queue pointer for exact-addressed messages: active owners wait until turn completion, and loaded idle owners can start without user input. Host installation and actual processing are verified separately (see [Listening while idle](#listening-while-idle) and [Waking Codex sessions](#waking-codex-sessions)).
- **Tasks and intercom:** on the operator's authority, a node starts, continues or stops a Claude Code or Codex task session for the runtimes its policy enables, and a session can open a conversation with a new session on a named node (see [Tasks](#tasks) and [Intercom sessions](#intercom-sessions)).

History: the node registry and read-only commands were the first step (GitHub issue #5); messaging, wake, tasks and intercom followed in issue #31 and its follow-ups (#63, #66, #74, #82, #88, #90).

## Session liveness (Phase 1 source)

Session states distinguish `running`, `idle-loaded`, `reachable-probable`,
`closed`, `archived`, `deleted` and `unknown`. A hook alone does not prove an
active Codex app; background task state does not prove a loaded desktop chat.
Archive/delete identity remains in a local tombstone after directory exclusion.
A stale hook or reused name cannot restore it. Unknown targets keep waiting
after one hour, and cannot enable autonomous queue, wake or legacy fallback.
An addressable UNKNOWN or terminal row also supplies no native MCP registration
or claim permission. Fresh `idle-loaded` evidence drives Claude delivery progress;
an old `idle` field without matching evidence remains uncertain.
Fresh complete closure metadata can only narrow the existing closed fallback;
all its original miss/minimum-age, listing, policy and permission gates remain.

Disk snapshots are diagnostic; autonomous admission additionally requires an
exact current-run source receipt from the daemon's one volatile authority.
Both publication lanes revoke before writing and grant after coherent success.
A persistence failure faults that authority until ordinary daemon shutdown;
restart begins empty and needs new source evidence. Cached positives cannot
regrant after failure. This does not preserve a terminal fact whose write failed.
Display history and the lifecycle ledger are bounded independently at 512;
terminal/restored records are preserved, and a full ledger makes every absent
identity UNKNOWN/capped. No new recovery command or permanent latch is added.

The existing daemon lane coalesces injected metadata observations every five
minutes and shares the publication generation with admission checks. Display
evidence expires after 60 seconds without renewal by republishing. Default
native capabilities are UNKNOWN: this source phase adds no native scanner or
launch command, and does not establish installation or native acceptance.
See [liveness architecture](ARCHITECTURE.md#session-liveness-metadata-phase-1-706).
The accepted 24-hour deadline is a later admission check before Kherep
queue/launch/resume, with a known gap before native turn start; it is not wired
in Phase 1.

## Architecture

```
injected metadata --> five-minute coalesced observation --> serialized liveness generation
shared generation --> truthful directory / deny-only admission / lifecycle tombstones
kherep-node --outbound WSS--> Worker kherep-control --> NodeSession Durable Object (one per node)
                                                   \--> Registry Durable Object (one per deployment)
operator ----HTTPS behind Cloudflare Access--> Worker --> Registry / NodeSession
owner CLI --> local outbox --> Registry grant / operation --> target journal --> measured result
verified MCP client --stateless HTTPS, disabled by default--> Worker --> Registry / online originating node
trusted Codex or Claude hook --> node --> prior intent with actual source session and call
native HTTP claim --> Registry: Codex session/thread/call, or Claude tool-use ID joined to prior intent
new native caller --> node sessions.snapshot --> Registry --> subsequent native intent registration
held Codex task intake --> bounded peer window --> known Codex inbox --> existing queue lane
successful original-owner Codex queue --> bounded metadata ticket --> serialized claim storage
trusted original-owner PostToolUse --> targeted ticket validation --> short hint --> existing Inbox receive
externally known safe reply ID + tuple + hash --> exact CLI preflight --> selected sent root
verified exact owner + selected root --> selected inbox lock/read --> tuple + hash check --> bounded JSON
```

While a Codex task intake waits, a bounded window keeps receipts, sender status,
outbox sends and incoming messages addressed by a recorded full Codex ID moving.
The existing queue lane may wake eligible interactive Codex targets; task threads
remain excluded. Commands, Claude delivery admission, new native intents and
authentication/reconnect stay on the original lane. Policy drift, unreadable or
missing policy, socket replacement and stop close this window. Already admitted
queue work retains its existing completion semantics. See [architecture](ARCHITECTURE.md).

The successful Codex queue path also publishes a bounded local metadata ticket
after rechecking policy, permissions, selected record addresses and depth.
Tickets carry at most eight message references and no peer content. Storage
serializes publication and claims; neither operation offers a message or creates
a delivery/read receipt. The Codex installer also projects an independent native
PostToolUse consumer for tool boundaries. It verifies the original owner and
excludes child agents before accessing storage, then validates only admitted IDs
against fresh policy and current records. One claimed generation emits one short
hint; the existing Inbox receive and confirming turn still own delivery state.
Actual active-turn Desktop and cross-host delivery remain separate acceptance
gates. See [busy-turn admission](ARCHITECTURE.md#codex-busy-turn-hint-admission).

### Protocol

Every frame is JSON text with one envelope:

```json
{ "v": 1, "type": "command", "id": "<uuid>", "seq": 3, "ack": 2, "ts": "<iso8601>", "body": {} }
```

- Types: `challenge`, `auth`, `register`, `capabilities.update`, `sessions.snapshot`, `command`, `command.ack`, `command.result`, `event`, `error`, `message.send`, `message.deliver`, `message.status`, `directory.get`, `directory`, `task.report`, `task.request`, plus the `mcp.*` frames described in [MCP.md](MCP.md).
- Server-to-node `seq` numbers are assigned to commands only; control frames carry `seq` 0. The node's `ack` is the highest command `seq` it has processed. Commands stay in the `NodeSession` log until acknowledged or answered, and a reconnect resends everything after the node's `ack` (at-least-once). The command `id` lets the node drop a duplicate without running it again.
- Liveness: the node sends the fixed frame `{"type":"ping"}` every 30 seconds. The Durable Object answers `{"type":"pong"}` through `setWebSocketAutoResponse`, which does not wake it.
- Offline detection: while a node is online, a `NodeSession` alarm runs every 5 minutes. It takes the later of the last message and the last auto-response; after 3 intervals without either, the node is marked `offline` in the registry and the alarm stops. A closed socket alone does not mark a node offline, so a reconnect within the backoff window does not flap its status.
- Reconnect: exponential backoff from 1 s with jitter, at most 60 s. A node whose key is unknown or revoked (close code 4403) stops instead of retrying.

### Commands

The operator API dispatches exactly the read-only commands `node.status`, `runtime.list` and `session.list`. The API refuses anything else, `NodeSession` refuses it again, and the node refuses it a third time against its local policy file, even when the command arrives authenticated. The local policy can narrow the set but never widen it; a malformed policy file allows nothing.

Item 5 adds the session commands `session.start`, `session.stop` and `session.continue`. A command body may carry `args`, validated strictly per command (`protocol-tasks.mts` `isCommandArgs`): the read-only commands take none, each session command exactly its own fields. The `commands` API never sends them; only the task dispatch does (see [Tasks](#tasks)). `NodeSession` refuses a session command whose args do not validate, and the node runs one only when its policy enables sessions. The args wait in the `NodeSession` outbox until the node acknowledges them and are not kept in the command history. A node that sends a `command` frame gets an `error`.

### Sessions

`session.list` and the `sessions.snapshot` frame report the agent sessions running on the node. A session carries `sessionId`, `runtime`, `state` and optional `startedAt` (ISO 8601), `name` (at most 128 chars), `cwd` (at most 512), `kind` (at most 32) and `label`. `name`, `cwd` and `kind` were added in Phase 2, `label` with issue #74; a node that omits them stays valid, and the Registry stores them as nullable columns that it adds to an existing `sessions` table on start. `label` is the display name of a task session that was started with one (letters, digits, space, `:`, `@`, `-`, `_` and `.`, at most 64 characters, no leading or trailing space), for example `intercom: claude@sekhmet`; the node adds it from its task record, found by session id or by the `task-<8>` name. `title` (issue #88) is the Codex thread title the Codex app shows: the daemon reads it for each Codex session (hook-recorded or task) from `<codex home>/session_index.jsonl` (the Codex home is `CODEX_HOME` when absolute, otherwise `~/.codex`), one JSON line per thread with `id`, `thread_name` and `updated_at`, measured with Codex app 0.158 alpha; the node reads only those three keys, and nothing else of the Codex history. The entry with the latest `updated_at` wins, on a tie the later line. The read is bounded (the last 2 MiB and at most 20,000 lines) and fail-soft: a missing, unreadable or garbled index, or a line without a usable title, gives no title and never a failed listing. A title has control, format and line-separator characters removed, whitespace collapsed, is trimmed and cut to 60 characters (ending in `…` when cut). It is display only and never an address. The Registry stores it in a nullable `title` column added on start; an older Worker ignores the field, so titles appear in the directory only once the Worker is updated, and an older node ignores a `title` it reads. The Registry session row `updated_at` records the last stored metadata change; an unchanged or merely reordered snapshot preserves it, while each directory response carries its own `fetchedAt` time.

- Claude Code: the node runs `claude agents --json` (see the [Claude Code sessions documentation](https://code.claude.com/docs/en/sessions)) with the `claude` executable found on `PATH`, without a shell and with a 10 second timeout. `status` becomes `state`, the epoch-millisecond `startedAt` becomes ISO 8601, `runtime` is `claude-code`. Unknown fields are ignored and malformed rows are skipped.
- Codex: Codex documents no session listing, so the node lists the sessions its delivery hook recorded in `codex-sessions/` and saw within the last 12 hours (`CODEX_ACTIVE_MS`), with `runtime` and `kind` `codex`, `state` `reachable-probable` before liveness normalization, and the name `codex-<last 8 characters of the id>` (Codex thread ids are UUIDv7, whose first characters are a timestamp, so sessions started within about a minute shared the earlier `codex-<first 8>` name; that name is still accepted as an address where exactly one live session has it, and a name two live sessions share addresses neither) (see [Codex sessions](#codex-sessions)).
- Codex tasks: the node also lists each Codex task it started, from `tasks/`, once its thread id is known and while it is active or was updated within the last 12 hours: `sessionId` the thread id, `runtime` `codex`, `kind` `codex-task` (`codex-intercom` for an intercom run the node started on its own, issue #198), the task's name (`task-<8>`), `state` `unknown` until independent holder/app evidence exists. A hook record for the same thread is listed once, as the task (see [Codex tasks](#codex-tasks)).
- A failed listing is not an empty one. Without `claude` on `PATH` the node reports no Claude sessions. When the command fails, times out or prints something other than a JSON list, `session.list` answers `ok: false` with the reason, and no snapshot is sent, so the Registry keeps its last known list instead of being cleared.
- The node sends a snapshot after every registration and then checks every 60 seconds, sending a new snapshot only when the list changed.

### Messages

A message goes from a session on one node to a session on another node. A session is addressed as `{ "nodeId": "<uuid>", "session": "<session id or name, 1-128 chars>" }`.

| Type | Direction | Body |
| --- | --- | --- |
| `message.send` | node to Worker | `messageId` (uuid), `fromSession`, `to` (address), `text` (1-16384 chars), optional `inReplyTo` (uuid), optional `taskId` (uuid), optional `proxyOf` (uuid, issue #408: a proxy answer to that message; never together with `inReplyTo`) |
| `message.deliver` | Worker to target node | `messageId`, `from` (address), `toSession`, `text`, optional `inReplyTo`, `createdAt` (ISO 8601), optional `taskId`, optional `proxyOf` |
| `message.status` | target node to Worker, Worker to sending node | `messageId`, `state`, optional `reason` (at most 256 chars), or strict metadata-only `progress` while `accepted` |
| `event` (`message.receipt`) | Worker to reporting node | `messageId`, `requestedState`, canonical `storedState`, optional `storedProgressAt` for accepted progress; acknowledges durable processing of a status report |
| `event` (`message.status.ack`) | sending node to Worker | `messageId`, `state` (`delivered`, `replied`, `refused` or `expired`); acknowledges a final status the sending node recorded (issue #308) |
| `directory.get` | node to Worker | empty |
| `directory` | Worker to node | `nodes` (`nodeId`, `name`, `status`), `sessions` (`nodeId`, `sessionId`, `state`, `runtime`, optional `name`, `cwd`, `kind`), `fetchedAt` (ISO 8601), optional `truncated`, optional `worker` (`capabilities`: what the Worker itself supports, `messaging.proxy.v1` since issue #408; a node holds it in memory for the connection the frame arrived on, cleared at every close and every authentication, never from `directory.json`) |

- States: `queued`, `accepted`, `delivered`, `replied`, `expired`, `refused`. A node may report `accepted`, `delivered` and `refused`; `queued`, `expired` and `replied` are set by the Worker only. Progress only moves forward; `refused` and `expired` are final. Only the target node of a message may report its state. While accepted, fixed `waiting`, `waking`, `fallback`, and `failed` progress codes explain the current local delivery stage. Progress carries timestamps only, cannot carry a free-text reason, and never advances or regresses the canonical state. A sender reads two further states derived from accepted progress (issue #197): `running` for `awaiting-turn-confirmation` and `fallback-running`, `stopped` for `operator-stopped` (`senderState` in `protocol-messages.mts`). They are never sent or stored, so Workers and nodes of older and newer versions keep validating the same frames. `running` reports the last observation, not liveness: progress is not refreshed while a run lasts, so a target that ended or crashed mid-run still shows `running` with its old `observedAt`. Every node from issue #396 on advertises `messaging.progress.v2` in `register`, meaning it reads every progress code; a sending node without it receives `cwd-refused` as `wake-not-authorized`, the code it validates. The Worker stores and audits the reported code and changes only what it sends to that sender.
- Acknowledgement (issue #308): the sending node answers each final `message.status` (`delivered`, `replied`, `refused`, `expired`) with the event `message.status.ack` once it has recorded that status in `sent/`. A message without a local `sent/` record, for example one sent through MCP, is acknowledged as well. A status the node could not record is not acknowledged, so it comes again with the Worker's next status replay. `queued` and `accepted` are never acknowledged. Every node advertises `messaging.ack.v1` in `register`. The acknowledgement is an `event` because a Worker that does not know it ignores unknown events; `message.status` and `message.receipt` keep their key-strict bodies. A Worker from issue #308 PR 4 on deletes the acknowledged message (see **Deletion** below); an older Worker ignores the event.
- Sender: the Worker takes the sending node from the authenticated connection, never from the body. A `from` field in `message.send` is ignored. Messages sent through the API carry the sender node id `operator` and the Access identity as the session.
- Idempotency: a repeated `message.send` with the same `messageId` from the same node creates no second message and is answered with the current state, also within 24 hours after the message was deleted (from its tombstone). The same `messageId` from another node is answered with an `error` frame.
- Routing: the Worker stores the message as `queued` and answers the sender with `message.status`. It sends `message.deliver` at once when the target node is connected, otherwise after the target's next successful authentication, oldest first. Status changes are forwarded to the sending node. After reconnect, the Worker replays the sender's unacknowledged metadata-only statuses (every `queued` and `accepted` row, and every final row whose current state its sender has not acknowledged) in bounded pages; duplicate or delayed statuses cannot move local progress backwards. `GET /api/messages` returns the canonical Worker state.
- Refusals: the Worker records `refused`, with a reason, and reports it to the sender when the target node is unknown or revoked, does not advertise the capability `messaging.v1`, or already has 100 queued messages. Revoking a node refuses every message still queued for it (reason `target node revoked`) and tells the senders.
- Expiry: a message still queued 24 hours after it was sent becomes `expired`, and the sender is told. Expiry is checked on every message operation and by a `Registry` alarm set to the earliest expiry of a queued message.
- Deletion (issue #308, PR 4): the Worker deletes a message row, metadata included, once its sender acknowledged the final status with `message.status.ack`: the sending node must be the acknowledging one, and the acknowledged state must be the stored, final one (`delivered`, `replied`, `refused`, `expired`); anything else is ignored, and a repeated acknowledgement changes nothing. An offline sender gets the final status from the reconnect replay and acknowledges it then, so the row stays until that happens. A message from the operator API, or from a sender that does not advertise `messaging.ack.v1`, is deleted 24 hours after its final state instead; revoking a node makes its final messages due at once. A row stored before the deletion existed (no `deletable` mark) is never deleted; an acknowledgement of its current final state settles it instead (issue #493): the Worker keeps the acknowledged state next to the row, writes an audit entry `message.settle` with ids only, and leaves the row out of the reconnect replay while the two states are equal. A later state (a reply to a delivered message) differs from the acknowledged one, so the row is replayed again and acknowledged anew; that holds also for a state change made by an earlier Worker version after a rollback. `queued` and `accepted` messages are never deleted. Deletion writes a tombstone (id, sender and target node, final state, reason, reply depth and `replyMessageId`; no text, no sessions) and an audit entry `message.delete` with ids only, in one transaction. A tombstone answers a late resend with the final status, a late target report with a receipt, MCP `status`, and task-control provenance; it is kept 24 hours. After that a late target report gets a receipt with the stored state `expired`, which settles every report. The `Registry` alarm deletes due messages and old tombstones in batches of 64 and runs again a second later while a batch was full.
- Only messages stored by a Worker from PR 4 on are ever deleted (`deletable` column, set on insert). Messages stored before that deploy keep their rows, whatever acknowledgements, replays, deadlines or revocations reach them; a one-time cleanup of them is a separate, approved operation.
- Reply depth: a proxy answer (`proxyOf`, issue #408) counts as one hop like a reply: its depth is its original's plus one, and a reply to it one more. The Worker stores the reply depth of every message: 0 without `inReplyTo`, otherwise the depth of the parent row or its tombstone plus one (a parent stored before PR 4 counts as 0), and 1 when the parent is unknown, for example after its tombstone was pruned. A message beyond `MAX_REPLY_DEPTH` (6) is stored as `refused` with the reason `reply depth exceeded`. The node-side depth guards stay.
- Accepted losses of deletion: `GET /api/messages` no longer lists acknowledged messages (the audit keeps their history, without text); a reply to a deleted message cannot mark it `replied`, so the sender keeps its acknowledged state; and once the tombstone is pruned, task-control registration and MCP `status` no longer find the message.
- The node advertises `messaging.v1` only when its policy has at least one accept rule (see [Node messaging](#node-messaging)). A `message.deliver` that the policy does not accept is answered with `message.status` `refused`, reason `not accepted by node policy`; an accepted one is stored in the node inbox and answered with `accepted`.

### Directory

The Worker answers `directory.get` from the Registry with every node that is not revoked and the sessions each node last reported; sessions of a revoked node never appear, and `startedAt` is left out. A directory that would not fit into one 64 KiB frame drops sessions from the end and sets `truncated`. Directory requests are not audited: nodes ask every minute, and the frame carries no message content. The Registry keeps the directory rows in memory and reads them again only after a write to nodes, runtimes or sessions (issue #308); a session snapshot that changes nothing is no write.

### Session messaging

The session tools and the daemon exchange plain files in the config directory (see [Node](#node)); there is no local socket. Every file is written atomically with mode `0600` in a directory with mode `0700`.

- The daemon asks for the directory after every authentication, every 60 seconds and within 2 seconds of a `directory.request`, and writes each answer to `directory.json`. A `directory.request` that comes less than 10 seconds after the last one the daemon honoured on this connection waits until those 10 seconds have passed, so a burst of `msg` calls asks the Worker once (issue #308).
- Every 2 seconds while connected, the daemon sends `message.send` for each outbox file not yet sent on this connection. The Worker's answer moves the file to `sent/` with its state; later statuses the Worker forwards update the same file. An outbox file the Worker has not answered 30 seconds after it went out (`SEND_RETRY_MS`) is sent again on the same connection, later resends of it back off (issue #308), and after a reconnect or daemon restart every unanswered outbox file is sent again at once (issue #195). This is safe because the Worker deduplicates by `messageId` and answers a repeat with the current state. A send that stays unanswered is repeated with exponential backoff while the connection lasts: the first resend exactly 30 seconds after the first send, each later one between half and all of 30 seconds times 2 to the power of the resends so far (equal jitter), at most 10 minutes apart. It is not logged per resend. The schedule starts over when the Worker answers and on every new connection. A malformed outbox file, or one the Worker rejects with an `error` frame, ends in `sent/` with the local state `error`.
- In the same round the node retries `accepted`, `delivered` and `refused` reports until an authenticated `message.receipt` event confirms Worker persistence. Each new state, or new accepted progress, of an inbox record is reported in the next round; a report without a receipt is repeated on the outbox schedule above (30 seconds, then backoff up to 10 minutes), which starts over on a new connection. A socket write is not confirmation. The Worker returns `requestedState` and canonical `storedState` only after committing the report, including duplicates; unknown messages and the wrong reporting node get no receipt. The node stores `reportedAt`, `reportedState` and canonical `workerState` separately in `inbox/receipts/<messageId>.json`, and daemon-owned progress in `inbox/progress/<messageId>.json`, so daemon writes cannot overwrite concurrent hook state. An outdated receipt cannot confirm a newer local state. Local `offered` reports as `accepted` until confirmed. Legacy optimistic markers in inbox records are ignored and retried after upgrade.
- The daemon reads the inbox through one in-process index (`node/inbox-index.mts`, issue #487). Each round validates it once, with one directory listing and one stat per record, and reads a record again only when it is new or its file changed (modification time, size or inode). The round's progress observers and status reports share that read; the Codex task resume reads the inbox once per round, not once per ended Codex task, and reads each waiting message it acts on again before deciding. Hooks and the CLI keep reading and writing the files directly, and the next round picks up what they wrote. A failed directory listing fails the round as before and is never an empty inbox; a failed stat reads that file again; every 10 minutes the whole index, cached receipts included, is rebuilt from the files. Only a receipt that settles a delivered or refused record is cached; receipts and progress of waiting records are read in every round.
- Every successful session listing is written to `sessions.json`, so the hook and the CLI map a Claude Code session id to its name without running `claude`.
- A successful listing may refuse accepted/offered records early with positive archive/delete metadata, or after the existing age bound with positive exact closure. It rechecks the current address and state under the record lock. Missing or unknown sessions remain waiting after the legacy 60-minute threshold. A failed listing refuses nothing.
- With `messaging.resumeClosed`, a message for a known session that is no longer running is delivered through an intercom session of its sender before that refusal ([messages for a closed session](#messages-for-a-closed-session)); every successful listing is also merged into `known-sessions.json` for this, which counts for each known session the listings in a row that did not show it (issue #389).

A threaded reply queued by the session still confirms local delivery, preventing an answered closed-session message from being refused later. The Worker independently records `replied` on the original message only when it stores a valid reply from its target node back to its original sender node and session. This status describes a stored response, not success of the requested work.

Upgrade the Worker before the nodes. A node relays a Codex fork's proxy answer (issue #408) only while its current connection has seen `messaging.proxy.v1` in a `directory` frame; against an older Worker it refuses every fork before admission (`fork-relay-unsupported`). Old nodes remain compatible but do not gain persistence receipts until upgraded; new nodes connected to an old Worker keep retrying reports because that Worker cannot acknowledge them. The protocol version and existing message states are unchanged. The same holds for `waiting/cwd-refused` (issue #396): a Worker before it answers such a report with `invalid message.status body`, so the target node keeps retrying it and the sender sees no newer progress for that message until the Worker is upgraded or the message reaches a final state.

#### CLI

On a host with a managed service, sessions run the stable command of the config directory (issue #436, see [Node](#node)); without one, `node modules/control-plane/node/cli.mts` of a checkout takes the same arguments. Task prompts and the delivery hooks name whichever of the two the host has (see [Tasks](#tasks)).

```sh
node "<config directory>/bin/kherep-node.mjs" msg sessions [--from <session>]
node "<config directory>/bin/kherep-node.mjs" msg send <node>/<session> [--from <session>] [--wait <seconds>] [--] <text...>
node "<config directory>/bin/kherep-node.mjs" msg send --reply-to <messageId> [--to <node>/<session>] [--] <text...>
node "<config directory>/bin/kherep-node.mjs" msg send <node> --new claude|codex --directive <the operator's answer, verbatim> [--cwd <dir>] [--from <session>] [--wait <seconds>] [--] <text...>
node "<config directory>/bin/kherep-node.mjs" msg inbox [--from <codex-session-id>] [--all | --receive [<messageId>] | --ack <receipt>]
node "<config directory>/bin/kherep-node.mjs" msg status <messageId>
node "<config directory>/bin/kherep-node.mjs" msg stop <taskId | sent messageId | owned requestId> [--expected-run-version <run version>] [--wait <seconds>]
```

- `msg sessions` prints every node of the directory with its sessions (the label if there is one, otherwise the name; the Codex thread title if there is one, as a double-quoted JSON string; id, state, runtime, cwd), for example `    codex-d7d07717  "Kherep-Funktionen nachschlagen"  019a...d7d07717  reachable-probable  codex  /work/repo`. A session without a title prints as before. A Codex session of this node whose record carries a last hook event (issue #408, see [Codex sessions](#codex-sessions)) adds it after the cwd, for example `  last event Stop at 2026-10-16T09:00:00.000Z`; sessions of other nodes and records without one print as before. A background task (issue #198) ends its line with `[background task]`: a Codex task or intercom run the node started (`kind` `codex-task` or `codex-intercom`), or a Claude Code session that `claude agents` reports as `background` or, unless reported `interactive`, that carries a task label. A note under the list says that such a task runs as a Control Plane task, not as a desktop app chat, that the desktop apps may not list it, and that `kherep-node attach <node>/<session id>` prints the command that opens its transcript and `kherep-node task status <taskId>` reads its status. `--from` marks the session it names, after the sender check below. The title is never an address: `msg send <node>/<title>` does not resolve by it and marks this session with `*`. A missing `directory.json` is an error that says the daemon may not be running, never an empty list; a directory older than 3 minutes is printed with a warning. Under each node header one line (issue #441) shows the control plane's queue for that node, apart from its connection status: `    intake: queue empty as of <fetchedAt>; last intake 3 min ago` (or `last intake: none recorded by the control plane`), `    intake: 2 queued, oldest 40 s as of <fetchedAt>; ...`, or, once the oldest queued message is older than 5 minutes, `    intake: NOT DRAINING: 3 queued, oldest 12 min (over 5 min) as of <fetchedAt>; last intake 25 min ago`. "Last intake" is the control plane's time of the node's last report that took one of its messages out of `queued` (accepted, delivered or refused). It is `intake: UNKNOWN (...)`, never an empty queue, when the Worker did not report it (an older Worker, or a truncated directory), when the directory is older than 3 minutes or dated more than 60 seconds ahead of this clock, or when the record is inconsistent. When any node is not draining, a closing note names `kherep-node doctor` (`queueDrain`, `intakeLatency`) and the daemon log's `lane` lines on that node as the next checks. No intake line carries a session id, name or message text.
- `msg send` resolves the node by id or name, then the session on that node by id, name or label. An unknown or ambiguous reference fails and lists the candidates, with one exception (issue #107): a full session id (a UUID, as Claude Code and Codex use) on a node the directory lists as `online` is sent even when the directory does not list that session, for example because it was closed, and `msg send` prints `note: session not listed on <node>; the node decides whether it can deliver` on stderr. Names, labels and `codex-<8>` still need a listed session; an unknown node, or a node that is not `online`, still fails. The address carries the resolved session id (names are for display and stay valid only until a rename); the target node's policy matches a rule by that id or by the session's current name in its `sessions.json`, and `*` as before. A message addressed by name, from an older sender or the operator API, still works as before. `--reply-to` sets `inReplyTo` and sends to the sender of that inbox message unless `--to` is given. The message is written to the outbox and its id printed; `--wait` waits for `accepted` or a refusal and exits non-zero unless the message was accepted. Put `--` before text that starts with `--`.
- The sender session is `--from`, preserved exactly, but only from a source this node can check (issue #200); it is never taken as typed. Without `--from`, the sender is the session of the runtime that runs the command (issue #471): the runtime is decided first, then its own variable names the session. `CODEX_THREAD_ID` names a Codex thread: Codex sets it for its shell commands to the thread running the command (source-defined in `codex-rs/protocol/src/shell_environment.rs`, not named in the Codex docs; measured with Codex 0.160.1 on macOS on 2026-10-17). `CLAUDE_CODE_SESSION_ID` names a Claude Code session; Claude Code sets it in Bash and PowerShell tool, hook and stdio MCP subprocesses ([environment variables](https://code.claude.com/docs/en/env-vars)). `KHEREP_SESSION_ID` names the node's own Codex runs and stays their identity; when the task's thread is known and differs from `CODEX_THREAD_ID`, the command is refused. Both runtimes' variables are inherited by child processes, so when both `CLAUDE_CODE_SESSION_ID` and `CODEX_THREAD_ID` are set (a `codex exec` started from a Claude Code tool, or a `claude -p` started from a Codex tool), one process listing decides within 12 ancestors (the executable, `ps comm`, on macOS and Linux; the command line on Windows): a `codex` program met first is Codex; the Claude Code process (`CLAUDE_PID`) met first is Claude only when a `codex` program sits above it, because an unrecognised Codex (a renamed binary, a path the command line split cannot read) could otherwise sit below it. Other `CODEX_*` names, such as the `CODEX_COMPANION_*` a Claude plugin sets, are no marker, and `CODEX_SESSION_ID` (the root session, which differs for subagents) is not used. A Codex thread named by `CODEX_THREAD_ID`, or a session a hook recorded, sends as its full id; other sessions use the name `sessions.json` records for their id, otherwise that id. When the runtime cannot be told (no process listing, no valid `CLAUDE_PID`, no decision within 12 ancestors, a missing or unreadable process on the way), when no variable is set, or when `CODEX_THREAD_ID` is not a plain id, the command exits 1 with a fixed reason and writes nothing; it never falls back to the other runtime's variable. `--from` behaves as before: it is accepted when it names that same session by id or name, or when it is the full id of a Codex session a Kherep hook recorded within 12 hours (`codex-sessions/<id>.json`, the same record `task new --from` requires) while `KHEREP_SESSION_ID`, if set, names the task run of that thread. When the runtime cannot be told, nothing in the environment verifies or blocks that id: the hook record identifies the caller, and the commands the Codex hooks emit (`msg inbox --from <id> --receive`, `msg send --from <id>`) keep working there. In that state the hook record is the only evidence `--from` can carry (issue #489): without a record from the last 12 hours, or with a `KHEREP_SESSION_ID` task that records another thread, the command stays refused, even when `--from` repeats `CODEX_THREAD_ID`, and the fixed reason for msg commands says so. A fresh record does not mean that the separate outbox filesystem access succeeds. Anything else, including a short `codex-<8>` alias, an id no hook recorded, an older record, or a name the caller only types, is refused with `is not a verified sender` and nothing is written. A Codex session without `CODEX_THREAD_ID` (unmeasured: the TUI, the desktop app, subagent threads, Windows) passes `--from <its full session id>`, which its `SessionStart` hook context names. Full Codex ids keep CLI responses compatible with native MCP reply provenance. The check guards against a mistaken or unknown sender; it is not authentication: the CLI identity remains what this node's processes report (see [Security model](#security-model)).
- `msg inbox` prints `proxy answer: <state> <relay id> at <time>` for a message an ephemeral fork of the session answered by proxy (issue #408; states `pending`, `handed`, `unconfirmed`, `taken`, `delivered`, `failed` with the quoted reason, `unresolved`), and `proxy for: <id>` for a received proxy answer.
- `msg inbox` lists undelivered messages for the current session. Codex supplies its recorded session id with `--from`, which passes the same sender check as `msg send`; `--all` includes delivered and refused records. Inspection also includes messages whose original address belongs to this session after a fallback handover, showing the current destination and available delivery task/session identity. Inspection changes no delivery state. The Codex-only `--receive` option emits up to 6 KiB of framed peer context for the current delivery target, marks newly accepted messages `offered` and returns an opaque exact-offer receipt for explicit processing ACK. The Maestro runs the ACK command after processing; the user performs no manual ACK. Repeating receive recovers already offered content without increasing attempts. Stop does not acknowledge Codex processing. Oversized messages have a full single-record `--receive <messageId>` path; see [Codex receipt contract](CODEX-RECEIPTS.md). It cannot be combined with `--all`. A record that was offered shows `  offered by: <offeredBy> at <offeredAt> (offer <offers>)` before its text, `unknown` for a record offered before issue #417. `msg status` prints the latest known sender state (`queued`, `accepted`, `running`, `stopped`, `delivered`, `replied`, `expired`, `refused`), or `pending` while the message is still in the outbox; while a sent message is `queued`, a second line (issue #441) names its target's queue from the same directory read, `  target <node> (<nodeId>) <status>; intake: ...` as in `msg sessions`, or `  target <nodeId>: intake UNKNOWN (...)` when the target is not listed (in a complete or a truncated directory) or there is no directory; later states add nothing, and the exit code is unchanged; `--wait` prints the same state and keeps its exit codes. The MCP `status` tool returns the same sender state as `senderState` and the silence reason as `hint` (see [MCP.md](MCP.md)). Accepted progress adds a fixed actionable description plus its observation and optional retry time. An accepted message without any progress 5 minutes after its last update (`ACCEPTED_SILENCE_MS`) is printed with a fixed reason naming the possible causes (target session not running, target node offline or on an older version) and `msg sessions` as the next check; it never prints target exceptions, paths, prompts, directives, task text, or summaries. It also lists each threaded reply that reached this node (issue #200) as `reply <messageId> from node <node>, session <session> (<inbox state>, received <time>)`, by the rule the Worker uses for `replied`: in reply to that message, from its target node, to its sender session (or to that address before a fallback handover). A reply that a node handed to an intercom session after its target closed (`closedTo` set, issue #389) is followed by indented lines `forwarded to: session <session>`, `delivery task: <taskId>` and `delivery session: <session>`, as far as recorded, so the sender sees where it went. An offered reply is followed by the indented `offered by:` line as in `msg inbox`. It lists every such reply still in this node's inbox (kept 7 days), each with its local state; the Worker's `replyMessageId` (see [MCP.md](MCP.md)) names only the one reply that marked the message `replied`, and the CLI does not read it. The reply keeps the original id in its `inReplyTo`; `msg inbox --all` shows its text with `in reply to: <messageId>`. For a message this node received rather than sent (issue #417), `msg status <messageId>` prints `<messageId> <inbox state> (received <time>)` and, once offered, the `offered by:` line, exit 0; an id in neither the outbox, `sent/` nor the inbox still exits 1.
- `msg stop <reference>` (issue #199) stops one background task without another peer message, through [owner task control](#owner-task-status-and-confirmed-stop): the reference is the task id, the id of a message this node sent, or an owned request id. It obtains fresh status, which resolves the reference to its task and current run, then submits a stop bound to that task and run (and to `--expected-run-version` when given), so it cannot reach a later run. It prints the request lines and results of `task stop`, then one verdict: `stopped: task <taskId>; its process and child processes ended at the target (task <state>)`, exit 0, only for a target result that confirms the stop of exactly that run; otherwise `not stopped: ...` (for example `task <taskId> has no running process (task failed, process closed); no stop was sent` after a failed run, or the target's error code) or `not confirmed: stop request <id> is pending`, exit 1. It waits up to 30 seconds (`--wait`) per request and needs `sessions.ownTaskControl` like `task stop`. A message delivered into an existing session (a resumed session, issue #241) starts no task of its own, so the Worker holds no grant for its id and status answers `source_not_found`. `msg stop` then looks up the message's target `<node>/<session>`: when the directory lists that session under the `task-<8>` name of exactly one task this node requested on that node, it prints `message <id> was delivered into the existing session <node>/<session> of your own task <taskId>; stopping that task (later messages to it wait until an explicit continue of that task)` and stops that task the same way (fresh status by task id, stop bound to its run). Like any task stop it records durable operator-stop intent, so every later message to that session waits with `operator-stopped` until an explicit continue clears it, not only the one message; `--expected-run-version` then refers to the task's run. Otherwise it answers `not stopped: message <id> was delivered into the existing session <node>/<session> (progress <code>), which matches no task you own; it cannot be stopped by message id`, exit 1, and sends no stop.

#### Delivery hook

`node/deliver-hook.mts` is a Claude Code command hook for `UserPromptSubmit`, `PostToolUse`, `Stop` and `StopFailure` ([hooks reference](https://code.claude.com/docs/en/hooks)). It reads the hook input from stdin and looks for inbox records addressed to the input's `session_id` or to that session's name in `sessions.json`. Its reply and receive commands name the stable launcher when the host's managed launcher resolves, as the task prompt does (see [Tasks](#tasks)), otherwise this checkout's `cli.mts`; the Codex mode below does the same.

Claude Code delivery is offer, then confirm. A hook call that injects a message marks it `offered` (counting `offers`, with `offeredAt`); only the next `Stop` marks it `delivered`, because `Stop` runs when the turn finished. `Stop` "does not run if the stoppage occurred due to a user interrupt", and API errors fire `StopFailure` instead ([Stop](https://code.claude.com/docs/en/hooks#stop), fetched 2026-09-25). Delivery is therefore at least once: a message can appear twice when a turn ends without `Stop`, for example after a user interrupt or a failed login, and it is never silently lost.

Each offer also records which path made it (issue #417): `offeredBy`, written with `offeredAt` and replaced by the next offer, so the last offer wins. A confirmed or refused record keeps it. Records offered before this field existed have none.

| `offeredBy` | Offered by |
|---|---|
| `wake` | Claude Code `UserPromptSubmit` of a turn the wake listener opened (it claimed the listener's marker, see [listening while idle](#listening-while-idle)) |
| `prompt` | Claude Code `UserPromptSubmit` otherwise: a user prompt, a prompt queued while a turn runs, or the first prompt of a resumed Claude intercom session |
| `stop` | Claude Code `Stop` continuing the running turn |
| `tool` | Claude Code `PostToolUse` inside the running turn |
| `codex-prompt` | Codex `UserPromptSubmit` |
| `receive` | `msg inbox --from <id> --receive` (Codex `Stop` continuation) |
| `codex-wake` | the daemon resuming an ended Codex task for its messages |
| `intercom` | the daemon handing messages for a closed session to a new or resumed Codex intercom session, or to a new Claude intercom session |
| `mcp` | an MCP `inbox` read that returned the record |

- `UserPromptSubmit` injects records in state `accepted`, and records in state `offered` only on evidence that the turn which offered them ended: `StopFailure` flagged them (`retry`), or the offer is older than 10 minutes (`REOFFER_AFTER_MS`; a user interrupt fires no hook). A prompt the user types while a turn still runs fires `UserPromptSubmit` too, so a younger offer is not repeated; that turn's `Stop` confirms it. A repeated record is marked in its block as offered again. After 3 offers without a confirming `Stop` the record becomes `refused`, reason `not confirmed by the session after 3 turns`, and is not offered again. Its offers read `offeredBy` `prompt`, or `wake` when the call claimed a fresh wake marker.
- `PostToolUse` (issue #388) injects records in state `accepted` into the running turn, after a tool call succeeded: Claude Code adds the context "alongside the tool result" and Claude reads it on the next model request ([PostToolUse](https://code.claude.com/docs/en/hooks#posttooluse), fetched 2026-10-12). It never offers an `offered` record again, and the turn's `Stop` confirms what it offered, so that `Stop` and a later `UserPromptSubmit` repeat nothing. A call from a subagent or in-process teammate (its input carries `agent_id`, with the parent's `session_id`) and a call in permission mode `bypassPermissions` inject nothing; those records wait for the next prompt. Parallel tool calls fire the hook concurrently, so a per-session lock file, `listeners/<session_id>.deliver.lock`, lets one call deliver while the others print nothing; a lock older than 5 seconds is removed. The call starts no turn: it neither checks nor spends the budget below and needs no `wake` policy. Without a waiting record or failure notice it exits before taking the lock. Its offers read `offeredBy` `tool`.
- `StopFailure` (the turn ended on an API error) flags the session's `offered` records `retry` and prints nothing; Claude Code ignores its output.
- `Stop` first confirms every `offered` record of the session as `delivered`, then injects only records still `accepted`, which arrived during the turn; the next `Stop` confirms those. A message offered in the same turn is never injected again, so a second `Stop` without new messages stays silent. `stop_hook_active` changes nothing: a continued or woken turn confirms and offers the same way. Its offers read `offeredBy` `stop`; `Stop` never reads or removes the wake marker. Continuing the turn is an autonomous turn: it draws on the session's budget (see [listening while idle](#listening-while-idle)) and never happens in permission mode `bypassPermissions`. When either stops it, `Stop` still confirms but offers nothing, writes `continue-budget` or `continue-permission-mode` to `wake.jsonl`, and the messages wait for the next user prompt. `UserPromptSubmit`, a prompt of the user, is not gated.
- `UserPromptSubmit`, `PostToolUse` and `Stop` also tell the session once about each message it sent (its `sent/` record has this session's id or name as `fromSession`) that ended `refused` or `expired`: `Your message <id> to <node>/<session> was not delivered: "<reason>"`. The record gets `noticedAt`.
- Receipts (issue #402): the same events tell the session once about each message it sent that reached `delivered`, which the target node reports only after the turn that carried it completed (issue #308): `Your message <id> to <node>/<session> was received (confirmed <time>).`, where `<time>` is the sent record's `updatedAt`, when this node recorded `delivered`: the Worker's status carries no timestamp. The line says "received", not by whom, because a fallback or intercom session may have taken the message (issue #389). A receipt matches the session by the record's `fromSessionId` (the sender's session id), and by its `fromSession` (id or name) only for a record without `fromSessionId` (from an older sender), so a renamed session still gets it and a later session reusing the name does not; failure notices keep matching `fromSession` only. No receipt is shown for `queued` or `accepted` (offered on the target) messages, nor for a message already `replied`. A reply that reaches this node (in reply to it, from its target node, to its sender session) records the sent message `replied` (issue #520): the daemon on arrival, the delivery hook at its next read, and every daemon start before its inbox purge, which runs after the daemon's first authenticated connection (or 60 s after its start without one), in the background in slices of about 50 ms (issue #581). So no receipt is shown for it, and the inbox's 7-day retention plays no part. The record gets `noticedAt`, the field failure notices set; a record is told at most once. A receipt never continues a turn: `Stop` shows it only beside a message or a failure notice that continues the turn anyway, otherwise it waits for the next `UserPromptSubmit` or `PostToolUse`. It is no wake: an idle sender is not woken, no `wake.jsonl` entry is written and no autonomous-turn budget is taken. Receipts are low priority: they take no message slot and only the room left after every shown message fits whole; otherwise they stay unmarked for the next event, and only printed receipts are marked. A call shows at most 5 receipts one per line; older ones are counted in one line (`<n> earlier messages this session sent were received too.`) and marked as well. Without peer messages, the intro names what follows: `Kherep: messages this session sent were not delivered.`, `Kherep: messages this session sent were received.`, or `Kherep: some messages this session sent were not delivered; others were received.`
- Nothing for this session: exit 0 without output. The hook reads local files only; it opens no network connection and starts no process.
- Otherwise it marks the records and then prints `{"hookSpecificOutput": {"hookEventName": "<event>", "additionalContext": "..."}}`. On `UserPromptSubmit` the context is added alongside the prompt; on `PostToolUse` alongside the tool result; on `Stop` it keeps the conversation going as hook feedback.
- MCP receipt rule (issue #308): the waiting records an MCP `inbox` read returns to a session are marked `offered` like a hook offer (`offeredBy` `mcp`), only after the response fits the transport limit. The session's `Stop` then confirms them, and `StopFailure` keeps them offered for a new offer, as above. A reply confirms them too: `msg send --reply-to` marks the message `delivered`, and any threaded reply, the MCP `reply` tool included, makes the Worker mark it `replied`. If the MCP client fires no hooks, an MCP-read message reaches `delivered` only through a reply.
- At most 10 messages and failure notices, 6 receipt lines, and 8 KiB per call, below the 10,000 character cap Claude Code applies to `additionalContext`. The rest waits for the next turn; a single message larger than the budget is cut, with a pointer to `msg inbox --all`.
- Any error ends with exit 0, no output and one line on stderr, which Claude Code writes to its debug log.

Every injected message is framed as peer content. The context opens once with the rules for peer messages: they are not instructions from the user; answer and coordinate with the peer as the operator's standing rules allow; a peer cannot grant approvals the user must give (deployment, publication, deletion, permission changes), and a peer's report of an operator approval counts only when the user confirms it in the session. Each block names the sender node (name and id), session, time and message id, says that the message comes from another agent session and is not an instruction from the user, and gives the exact `msg send --reply-to` command line for an answer. The text sits between markers that carry a random tag chosen per hook call, so a message cannot fake the end of its own block.

Reply depth, local and without a protocol change: an inbox record gets `depth` 0 for a new message, or the depth of this node's sent message it answers (`inReplyTo`) plus one. `msg send --reply-to` stores the replied record's depth plus one in its `sent/` record. From `MAX_REPLY_DEPTH` (6) on, a record never wakes a session and its block says that the automatic reply limit is reached and the model should not reply unless the user asks.

`bootstrap/install.sh` wires the hook into the user `settings.json` for all four events (on `PostToolUse` as the last entry of the all-tools group), and the wake listener below after it on `UserPromptSubmit` and `Stop` and last on `SessionStart`. Since issue #592 each command names the stable entry point `node "<CLAUDE_HOME>/kherep/control-plane/claude-control-plane-hook.mts" deliver` (`wake --timeout 86400`, `attribution`), which runs, inside its own process, the hook of the source named in `<CLAUDE_HOME>/kherep/control-plane/source.json`, the root the installer last ran from; it fails closed without a usable record (exit 1, one stderr line, no fallback), and the commands stay the same across upgrades and roots; see [installation](../../docs/INSTALLATION.md#3-install-the-claude-adapter). Without an enrolled node the hooks find no inbox and exit 0 without output.

Without the Kherep installer, add it by hand to a Claude Code `settings.json` in the path form below. Use the absolute path of your checkout, and give the hook the same `KHEREP_CONFIG_DIR` as the daemon when the daemon uses one.     ] }],
    "Stop": [{ "hooks": [
      { "type": "command", "command": "node \"<checkout>/modules/control-plane/node/deliver-hook.mts\"", "timeout": 10 },

    ] }],
    "StopFailure": [{ "hooks": [{ "type": "command", "command": "node \"<checkout>/modules/control-plane/node/deliver-hook.mts\"", "timeout": 10 }] }],

#### Listening while idle

`node/wake-hook.mts` wakes an idle Claude Code session when a peer message arrives. It runs with `"asyncRewake": true`, which "runs in the background and wakes Claude on exit code 2", and wakes it "immediately even when the session is idle" ([hooks reference](https://code.claude.com/docs/en/hooks), fetched 2026-09-25). A process the model starts itself is no substitute: a background listener started through the Bash tool was blocked by the auto-mode classifier.

Waking is on by default (operator decision of 2026-10-12, issue #390). It acts only on messages the `messaging` section accepted ([Node messaging](#node-messaging)), and that section is never implied for an existing file. A policy file without a `wake` section acts as `{ "enabled": true, "sessions": ["*"], "codexApp": true, "replies": true }`, and `kherep-node node onboard` writes that section into a new `policy.json` (an existing file is never rewritten). An operator narrows it by writing the section, or opts out with `"wake": { "enabled": false }`. The `wake` section names the sessions, by id or current name, that may be woken; `"*"` stands for every session. The wildcard is sufficient when `UserPromptSubmit` or `Stop` supplies a permission mode. A `SessionStart` without that field needs the full session id or its current unique name in this list, a known safe mode and a successful launch check:

```json
{
  "version": 1,
  "allowedCommands": ["node.status", "runtime.list", "session.list"],
  "wake": { "enabled": true, "sessions": ["review", "7f9c2d1e-0b4a-4c1e-9a55-3c2f8e6d1a90"] }
}
```

A missing section is the default above. `"enabled": false` is the explicit opt-out; any other `enabled` value than `true`, or an empty or malformed `sessions` list, turns waking off as well (fail closed) and leaves the rest of the policy in force; a policy file that does not parse denies everything as before. `codexApp` and `replies` must be booleans when present; with either `true` the `sessions` list may be empty or absent (see [Waking Codex sessions](#waking-codex-sessions) and the reply grant below). `nativeQueue` (issue #429) must be a boolean when present as well; only `true` turns on the native Codex Queue pointer producer, it grants nothing by itself, and the default (absent, also in the built-in section) is off. A change of `nativeQueue` in either direction invalidates the current CP admission of every Codex owner once, as any policy edit does; the next poll readmits. A session that is not listed, has no task grant and no reply grant to listen for gets no listener, and the audit says `not-allowlisted`, once per listener; the one exception is a session whose id the node is still mapping (see the task grant under [Tasks](#tasks), issue #109). The allowlist governs wakes only: a `Stop` continuation extends a turn the user started, so it is limited by the budget and the permission mode below, not by the list.

Reply grant (issue #253, operator decisions of 2026-10-05): with `"replies": true` in the `wake` section, a reply may wake the Claude Code session that sent the original message without that session being listed, so a session that asks a peer something and goes idle gets the answer without a per-session entry:

```json
{ "wake": { "enabled": true, "replies": true } }
```

It is a per-message grant like the task grant, not a listing. An unlisted Claude Code session keeps its listener and wakes only for granted records; every other guard applies as before: kill switch, permission mode (the `SessionStart` checks still need an explicit listing), reply depth, and the budget and spacing. A record is granted only when all of these hold, judged at every poll; anything else, or a sent record that cannot be read, grants nothing:

1. Its `inReplyTo` names a message in this node's `sent/`, and it comes from a node, not from the operator API.
2. It comes from the node the original was sent to. The Worker sets the sender node from the authenticated connection but does not check `inReplyTo`, so a third node that only knows a message id gets no grant.
3. The original was sent from this session. `msg send` keeps the sending session's id as `fromSessionId` in the outbox and `sent/` record, next to `fromSession`, which is often its renameable name; the id never goes to the Worker. The id must match. A sent record of an earlier version without the id matches by its `fromSession` instead, which ends with the age bound.
4. The original is at most 24 hours old by its `createdAt` (this node's clock, not later than now) and not `refused`, `expired` or `error`; a `queued` original grants.

Every reply to the same original arrives at reply depth 1, so the depth limit does not bound how often replies to one message wake the session within the 24 hours; the turn budget and spacing do. A `SessionStart` input without `permission_mode` (for example a resume) runs the launch check only for an explicitly listed session, so a session that only the reply grant covers does not arm there (`permission-mode-unknown`, fails closed); it arms at its next `Stop` or prompt.

With `replies` on, every idle Claude Code session on the node keeps a 24-hour listener and takes one re-arm turn a day, as with `"*"`. The audit names the grant: `wake`, `backlog` and `stuck-offer` lines of reply-granted records carry `"grant": "reply"`, those of task-message-granted records (below) `"grant": "task"`. Turning the switch off ends a listener that is neither listed nor holds a task grant, audited `not-allowlisted` (issue #213). The switch applies to Claude Code listeners only; Codex sessions keep their own paths (see [Waking Codex sessions](#waking-codex-sessions)), where a reply to a Codex task session already carries its task id.

Task message grant (issue #264): the same switch also lets the messages of a task the session requested wake it. A task started with `msg send <node> --new` is told to answer with a plain `msg send` to the requesting session, and every message a task session sends carries its task id but no `inReplyTo`, so the reply grant does not cover it. A record is granted only when all of these hold, judged at every poll; anything else grants nothing, and so does every task message while any file in `task-requests/` cannot be read, since it could claim the same task:

1. Its task id names a task request of this node (`task-requests/`) in state `dispatched`, claimed by no other request, and it comes from a node, not from the operator API.
2. It comes from the node the Worker dispatched the task to (the request's `nodeId`).
3. The task was requested from this session. `msg send --new` and `task new` keep the requesting session's id as `requestedBySessionId` in the request file, next to `requestedBy`, which is often its renameable name; the id never goes to the Worker. The id must match, also when the name matches. A request without the id, written by an earlier version, matches by its `requestedBy` instead.
4. The request is at most 24 hours old by its `createdAt` (this node's clock, not later than now). The task's lifetime is not observable on the requesting node, and a resumed task runs with a fresh deadline, so the bound counts from the request.

The grant covers every message of the task, not only its first answer. A plain `msg send` from the task arrives at reply depth 0, so the depth limit does not bound these wakes; the turn budget and spacing do. It applies to Claude Code listeners and their delivery progress only; a Codex requester is out of scope, as for the reply grant. Risk accepted with it, the same class as the reply grant: the Worker accepts a task id only when the sender's or the target node runs the task, and it does not check that the sender is the task's own session, so any session or local process on the task's node can carry the task id and wake the requesting session within the 24 hours, bounded by the budget. It cannot wake any other session.

Turn budget (issue #259): the optional `budget` object in the `wake` section sets the per-session [budget](#listening-while-idle) of autonomous turns, which is otherwise 20 per rolling hour, 100 per rolling day and 30 s between two (operator decision of 2026-10-12, issue #390):

```json
{ "wake": { "enabled": true, "sessions": ["review"], "budget": { "perHour": 30, "perDay": 200, "spacingSeconds": 30 } } }
```

A listener's daily re-arm also takes a turn, so a very low `perDay` can be used up by re-arms alone. The budget belongs to an accepted, enabled `wake` section: with `enabled` other than `true`, a rejected section or no section (the default section has no budget), every autonomous turn (the `Stop` continuations and closed-session delivery included) keeps the defaults. Each field is optional and falls back to its default. Each must be an integer within hard bounds, so that a policy can loosen the budget but not remove it: `perHour` 1 to 60, `perDay` 1 to 500, `spacingSeconds` 5 to 3600; an explicit `perDay` must be at least an explicit `perHour`; `perDay` alone caps the day, also below the default hour, so `{ "perDay": 10 }` means 20 per hour and 10 per day; without `perDay` the day allows at least `perHour` turns, so `{ "perHour": 30 }` alone means 30 per hour and 100 per day. An out-of-range, non-integer or inverted value, an unknown key or a `budget` that is not an object rejects the whole `wake` section (fail closed, as for `codexApp` and `replies`): waking is off and the defaults apply. The one budget applies to every autonomous turn: Claude Code wakes and re-arms, the `Stop` continuations of the Claude and Codex delivery hooks, the Codex task resume and `codex queue` wake, and messages for a closed session. The listener reads it with the policy at every poll, the delivery hook when a `Stop` would continue the turn, and the daemon at its start. `kherep-node doctor` shows the effective budget.

- Armed twice per turn: after the delivery hook on `UserPromptSubmit` and on `Stop`. The `UserPromptSubmit` entry keeps a listener when a turn ends without `Stop` (`StopFailure` or a user interrupt); it states its timeout, because `UserPromptSubmit` hooks otherwise default to 30 s. Each arming takes over `listeners/<session_id>.json` (a random token, pid, start time, event) in the node directory; a listener that finds another token there exits 0, so one session never has two listeners. Identity is the token, never the pid, and no listener terminates another process. `stop_hook_active` does not matter.
- Armed at `SessionStart` too (issue #97), which "Runs when Claude Code starts a new session or resumes an existing session" with `source` `startup`, `resume` (`--resume`, `--continue`, `/resume`), `clear`, `compact` or `fork` ([hooks reference](https://code.claude.com/docs/en/hooks), fetched 2026-09-27). Because this input has no `permission_mode`, it arms only for an explicitly listed session after the stored or transcript mode, settings and fresh launch checks all pass. A wildcard, reply grant or task grant does not satisfy that restart prerequisite. The listener ends the `SessionStart` group, after the existing hooks, and records the `source` in its lock. The session counts as idle there; a prompt that follows arms at `UserPromptSubmit`, whose listener takes the lock over, so the `SessionStart` one exits as `superseded`. After `compact` the session counts as busy, as at `UserPromptSubmit`, because auto-compaction runs inside a turn.
- Backlog (issue #101): a listener armed at `SessionStart` also wakes the session once for messages that arrived while no listener ran, that is `accepted` records of the session received before its start or within its first 3 s; no delivery hook runs at a Claude Code `SessionStart`, so nothing else offers them before the next prompt. It waits 8 s first, so a prompt typed right after the resume comes first: its `UserPromptSubmit` delivers the messages and its listener supersedes this one. Before waking it waits 250 ms and re-reads the records, and wakes only for those still `accepted`; the woken turn's `UserPromptSubmit` offers them, so the listener and the delivery hook never make two turns for one message. Each record is woken for once at most (`listeners/<session_id>.stuck.json`, shared with stuck offers), audit `backlog`. All other guards apply: kill switch, allowlist or task grant, the permission mode checks, reply depth and budget. Listeners armed at `UserPromptSubmit` or `Stop` leave such records to their delivery hook.
- A listener armed at `UserPromptSubmit` (or at `SessionStart` after `compact`) treats the session as busy: it wakes only after `StopFailure` marks it idle (the delivery hook does that) or once the turn cannot still run (10 minutes, as for re-offers). A turn that ends normally fires `Stop`, whose listener replaces it. Caveat: a turn that runs longer than 10 minutes can get a wake that becomes a short extra turn after it.
- Policy changes (issue #213): at every poll the listener reads the policy file again and decides with it whether the session is listed, so a session added to `wake.sessions`, or `"*"`, is woken by the listener that is already armed, also one that so far listened on its task grant alone. A policy edit cannot create that native listener or attach `asyncRewake` after its owner hook exited. A new association needs a genuine owner hook event; fabricated listener files, a detached listener or a copied `--resume` process are not equivalent. A session no longer listed, or a `wake` section turned off, ends a listener without a task grant (removing the section restores the default, which lists every session): it releases its lock and audits `not-allowlisted`; one with a grant keeps listening for the grant's messages. A policy file that turns unreadable or malformed leaves the last policy read in force for a running listener, audited once as `policy-unreadable`; a listener armed then still fails closed. A missing file is the default policy, with the default `wake` section. The `SessionStart` checks (explicit listing, permission mode) apply only when the listener is armed. The listener keeps what it currently wakes for in `listeners/<session_id>.scope.json` (`token` of its lock, `listed`, the task id of its grant, `replies` while the reply grant is on, and its lock's `order`), which the daemon's delivery progress reads.
- It polls the inbox every 2 s for `accepted` records addressed to the session id or its current name that were received more than 3 s after it started. Earlier arrivals belong to the delivery hook of the same event, which runs in parallel. Race: a message that arrives within those 3 s and after that hook read the inbox waits for the next turn. Before waking it waits 250 ms and re-reads the records, so one a delivery hook offered meanwhile wakes nobody.
- Stuck offers: an `offered` record of the session that the delivery hook would offer again (`StopFailure` flagged it, or it is older than 10 minutes) wakes the idle session once, with `Kherep: a message offered in an earlier turn may not have been read. It is offered again in this turn.`, so that turn's `UserPromptSubmit` offers it again. Never more than once per record (`listeners/<session_id>.stuck.json`), and not in the first 3 s, while the parallel `Stop` may still confirm it.
- On a hit it exits 2 with `Kherep: N new message(s) from other agent sessions arrived. They are delivered in this turn.` on stderr, which Claude Code shows as a system reminder. The texts carry no peer content. Measured on Claude Code 2.1.273: the woken turn fires `UserPromptSubmit` with that text as prompt, so the delivery hook offers the messages at its start; its `Stop` confirms them and starts the next listener.
- Wake marker (issue #417): right before it exits 2 for messages (fresh, backlog or stuck, not for a re-arm) the listener writes `listeners/<session_id>.woke.json` atomically, `{wokenAt, token, messageIds}` with its lock token and the ids it woke for; no message text. A failed write never stops the wake. The next `UserPromptSubmit` of the session removes the marker whatever it holds and, when it was written at most 30 s before (`WAKE_CLAIM_MS`), labels every record that call offers `offeredBy` `wake`; otherwise `prompt`. The delivery hook never reads the input's `prompt` field; whether that still equals the wake text is not relied on. `Stop` and `PostToolUse` neither read nor remove the marker. Races, accepted: a wake that opens no turn leaves a marker, so a user prompt within 30 s reads `wake` (`wake.jsonl` still shows the wake); a user prompt in the sub-second window between the listener's exit and the woken turn's prompt claims it first. A woken turn whose messages a `Stop` continuation already offered finds nothing to label; those read `stop`. Known limitation: a resumed Claude intercom session (`claude --resume … --bg`) gets no marker, so its first offer reads `prompt`; its `closedTo` and delivery task identify that path.
- Timeout: Claude Code enforces `timeout` on an `asyncRewake` hook and kills it without waking the session, which would leave the session deaf. The installed command passes the same number as `--timeout <seconds>`, and the listener exits 2 on its own 60 s before it with `Kherep: message listener re-armed.`: one short turn a day, which re-arms. A `--timeout` of 120 s or less ends the listener at start; without the argument it assumes 86400.
- Budget: wakes, re-arms and `Stop` continuations of the delivery hook are all autonomous turns and share one budget per session, `listeners/<session_id>.turns.json`: at most 20 per rolling hour, 100 per rolling day, and 30 s between two, unless `wake.budget` sets other values (see the turn budget above). Each spend reads and rewrites that file under an exclusive lock file (`<file>.lock`, taken over when older than 5 s); a process that cannot get the lock within about half a second is denied the turn, never granted it blind. Within the 30 s, or while the lock is held, the listener waits and tries again; with the hour or day used up it exits 0 (audit `budget`) and the messages wait for the next user prompt, whose listener starts again. Records at `MAX_REPLY_DEPTH` (6) or deeper never wake.
- Permission mode: a session whose hook input says `permission_mode` `bypassPermissions` is never woken (audit `permission-mode`) and its `Stop` does not continue the turn; `default`, `acceptEdits`, `plan`, `auto` and `dontAsk` may be woken. The mode is read when the listener is armed. A `SessionStart` input carries no `permission_mode` (measured on Claude Code 2.1.258), so every arming stores the mode its input reported in `listeners/<session_id>.mode.json`. A `SessionStart` without the field arms only when all of these hold (operator decision of 2026-09-27, fail closed); otherwise it exits 0 with the audit `permission-mode` where bypass was found and `permission-mode-unknown` where it could not be ruled out:
  1. A stored mode exists and is not `bypassPermissions`. Without one (issue #101), the mode of the last user entry in the session transcript at the input's `transcript_path` counts and is stored: Claude Code 2.1.258 writes `permissionMode` on the user entries of that JSONL file (measured 2026-09-27). The node reads at most the last 2 MiB, only lines that parse as JSON objects, and only their `type` and `permissionMode` fields; it never keeps or logs message content. The path must be absolute and name a regular file, not a symlink, under `projects/` of the Claude config directory (`$CLAUDE_CONFIG_DIR`, else `~/.claude`), also after resolving links (`node/transcript-mode.mts`). A missing, foreign, unreadable or unparseable transcript, or no user entry with the field in that window, refuses with `permission-mode-unknown`; `bypassPermissions` there refuses with `permission-mode`.
  2. The session is listed by id or name, not only through `"*"`.
  3. `permissions.defaultMode` is not `bypassPermissions` in the user settings (`$CLAUDE_CONFIG_DIR/settings.json`, else `~/.claude/settings.json`) or in `.claude/settings.json` and `.claude/settings.local.json` under the input's `cwd`. A missing file is no layer; an unreadable or unparseable one, or no absolute `cwd`, refuses.
  4. None of the 4 processes above the hook (`node/launch-mode.mts`) carries `--dangerously-skip-permissions` or `bypassPermissions` (as `--permission-mode` value or in inline `--settings` JSON), and none passes `--settings` with a file. The node takes one process listing (Windows: `powershell.exe -NoProfile` with `Get-CimInstance Win32_Process`; macOS and Linux: `ps -A -ww -o pid= -o ppid= -o args=`) with a 10 s timeout and no pid in any command; a listing that fails, a parent missing from it, or a command line it cannot read refuses. A pid missing further up has exited and ends the walk, because the Claude Code process running the hook is alive. Measured on Windows (2026-09-27): the Claude desktop app starts `claude` with `--permission-mode <mode>` and inline `--settings "{...}"`, and the listing took about 0.4 s.

  A prompt or `Stop` that arms while this check runs keeps the lock; the `SessionStart` listener then exits as `superseded`. `UserPromptSubmit` and `Stop` are judged by their input's `permission_mode` as before.
- Parent death: every poll checks that the process that started the listener still runs; if not, the listener exits 0 (audit `parent-gone`). On macOS and Linux an orphan is re-parented, so its parent pid changes; on Windows the parent pid stays and is probed with signal 0. Claude Code may start the hook through a shell; when that shell stays alive as the parent, the listener watches the shell, and after Claude Code exits it ends at the latest at its timeout. A reused pid on Windows can hide a parent's death.
- Stale locks (issue #225): the daemon removes the lock of a listener whose process is gone, at its start and then hourly: a lock whose pid is not running or whose content is not JSON. A lock whose pid another process reuses stays until that process ends. A resuming session's new listener may write its scope and lock at any moment, so the daemon never deletes by path: it renames the file to a tombstone, deletes it only if its bytes still equal what it judged, and otherwise links it back without overwriting. If a file took the place meanwhile (a `SessionStart` listener whose check found no lock, or another sweep's recovery), the later-armed lock keeps the path, and a dead listener's lock never displaces a live one: an older one in place is taken aside the same way and dropped. Arming order is the lock's `order`, the larger of the arming time and one more than the lock and scope in place, so a later arming orders after the listener it replaces even when the clock stepped back or within one millisecond; `startedAt` stays the real time for the deadline and every age, and a lock or scope without `order` (an older version) orders by its `startedAt`. A listener that finds its lock gone while its scope file carries its token, or an older listener's `order`, puts it back the same way; one whose scope names a later listener, or has no `order`, stands down as before. A listener that finds an older listener's lock in place writes its lock and scope back, so the later-armed listener always keeps the session. A `SessionStart` listener stands down when a token appears in the lock or scope during its launch check that was in neither before, which needs no clock either; a read that failed, before or after the check, never makes it stand down (a failed read is retried once after 25 ms, and is never taken for a missing file). The scope file goes with its lock only while it carries that lock's token. The session's other files stay while the node can resume it: they arm a resumed session, keep its budget and keep a record from waking twice. A `.woke.json` stays until the session's next prompt removes it.
- Ended sessions' state files (issue #474): in the same hourly pass the daemon removes a session's `.mode.json`, `.turns.json`, `.scope.json`, `.stuck.json`, `.woke.json`, `.queued.json`, `.busy-hint.json` and `.busy-admission.json` once all of these hold: a fresh, complete listing (`sessions.json` no older than three minutes, no unseen runtime) does not show the session; `known-sessions.json` no longer holds it, which is 7 days after the last listing that showed it, so closed-session delivery can no longer resolve it; no lock, in-flight lock or temporary file of it exists; no active task record names it; and every one of its state files is older than 7 days. A stale, partial or missing listing, or an unreadable `sessions.json`, `known-sessions.json`, task record or listener directory, removes nothing. Each file is taken aside by the same rename and compare and put back when it changed meanwhile; at most 200 files go per pass, the rest an hour later. `.queued.json` has had no writer or reader since 2026-10-11 and goes with the rest. A session resumed after more than 7 days without a listing has no remembered mode at `SessionStart`; its listener falls back to the transcript and the launch check, and the first prompt remembers the mode again. A tombstone a sweep left unfinished is linked back after a minute, newest wins as above. Each failure is logged with its error code. A listener directory or lock that cannot be read is logged, never taken for an empty directory or a dead lock.
- Headless runs (issue #235): a print-mode run (`claude -p`) can never be woken, so its listener ends before its first poll. The [hooks reference](https://code.claude.com/docs/en/hooks) says that with `-p` "Claude Code kills any async hook still running at teardown" (fetched 2026-10-05), yet on Claude Code 2.1.289 (Windows, 2026-10-05) a `claude -p` run waited for the listener, its only child process, until the 24-hour timeout. The listener arms as any other, so the order of the session's listeners stays the order they armed in; then, before its first poll, it decides the run mode (`node/headless-mode.mts`) from one process listing. The first Claude Code process among the 4 above the hook counts: program `claude`, `claude.exe` or `claude.cmd`, `node` running a script named `claude`, or a `@anthropic-ai/claude-code` script; a `-p` above it, such as Windows Terminal's `-p <profile>`, never counts. In this order: (1) a process of the `--bg` machinery, or one whose parent is, is interactive, whatever its environment. Measured on Claude Code 2.1.289 (2026-10-05): on Windows a `--bg` session runs under `claude.exe --bg-pty-host …` and takes its prompt as a positional argument; on macOS the session is `claude bg-spare …` (a pre-warmed spare, without session id, name or prompt) under `claude bg-pty-host --bg-pty-host …` under `claude.exe daemon run …`. The option `--bg-pty-host` and the subcommands `daemon run`, `bg-pty-host` and `bg-spare` mark it, never on a process with `-p`, `--print` or `--print=…` among its own options (issue #245: `ps` loses the quoting, so `claude "daemon foo" -p` would read like the daemon); no `--session-id` is relied on, and the daemon's `--spawned-by` JSON is never read as options; this covers the daemon's task and intercom sessions, which the daemon also starts without its own `CLAUDE_CODE_ENTRYPOINT` and `CLAUDECODE`. (2) `CLAUDE_CODE_ENTRYPOINT` `sdk-cli`, the value measured for `claude -p` (not in the [environment variable reference](https://code.claude.com/docs/en/env-vars), checked 2026-10-05), is headless; any other value decides nothing, because `claude --bg` reports `cli` and a `claude -p` started inside a session inherits that session's value. (3) The process's own option `-p`, `--print` or `--print=…`, a whole argument before any `--`, is headless, anything else interactive. Windows command lines are split as Windows does (`CommandLineToArgvW` and the C runtime rules), so a `-p` inside a quoted prompt (`"mkdir -p build"`) is no option. No such process, a missing parent, an unreadable command line or a failed check leaves the mode unknown, and an unknown or interactive run keeps listening (fail open, operator decision of 2026-10-05). A headless run removes its lock and scope, each only while it still carries its own token, and the mode file only when this arming created it and no newer listener took over; it exits 0 with the audit `headless` without polling or waking. A `claude -p` turn audits up to three such lines. That such a hook exits 0 at once and leaves no listener files is checked by the spawn test in `node/wake-hook.test.mts`; there is no wall-clock bound, because node start-up alone comes close to one second on Windows (issue #245). The decision is kept per Claude Code process (issues #245, #248) in `run-modes/<session_id>.<pid>.json` in the node directory (mode, `CLAUDE_CODE_ENTRYPOINT`, time; written atomically), so only the first hook of a process lists processes. The pid is `CLAUDE_PID`, which Claude Code sets to its own process id in the subprocesses it spawns, hook commands included ([environment variables](https://code.claude.com/docs/en/env-vars), read 2026-10-06), and which survives a shell between Claude Code and the hook; a `claude -p` started inside a session sets its own (measured 2026-10-06 on macOS and on Windows). Without a plain pid above 1 in `CLAUDE_PID`, the hook's parent pid stands in. An entry decides only for the same session id, pid and `CLAUDE_CODE_ENTRYPOINT`, for at most one hour; only a check that found the Claude Code process and read its parent's command line is kept, a full check prunes entries older than an hour, and any read or write error means a full check. Measured in process on macOS (2026-10-05, about 970 processes, node start-up not included): a full check takes a median of 38 to 43 ms, a kept decision 0.02 to 0.03 ms. Claude Code on Windows starts each hook through Git Bash, so every hook has a fresh shell as its parent; keyed on `CLAUDE_PID`, the hooks of one Claude Code process still share one entry. Measured on Windows (2026-10-06, issue #248), a full listing takes 348 to 362 ms per hook. When the key is the parent pid and that parent is a shell (program `bash`, `sh`, `zsh`, `dash`, `cmd`, `pwsh` or `powershell`), that pid comes back for no other hook, so nothing is kept or pruned and each such hook is checked in full. A `claude -p --resume <id>` of an idle interactive session is headless: it runs in another Claude Code process with its own pid and gets its own check. Its listener takes over the session's lock and scope like any arming, so the interactive session's listener stands down, and the headless one then ends (`headless`); the interactive session listens again from its next own prompt. There is no re-arm in between (decided on issue #245). Known false positive: on macOS and Linux `ps` loses the quoting, so a session outside the `--bg` machinery (an interactive `claude "…"` in a terminal) whose positional prompt holds a separate `-p` or `--print` is taken for headless. Known residual: a `claude -p` started directly by such a session whose prompt begins with `daemon run` and holds no separate `-p` takes that session for the daemon and keeps listening. Operator escapes that keep the hook out of a run: `--bare`, `--safe-mode`, `--settings '{"disableAllHooks":true}'`, or `wake.disabled`.
- Kill switch: while `wake.disabled` exists in the node directory, listeners exit at start. Without an enrolled node (`node.json`) or with waking turned off in the policy they exit 0 and write nothing.
- Audit: `wake.jsonl` in the node directory gets one line per decision, `{ts, sessionId, messageIds, action[, grant]}`. The listener writes `wake`, `backlog`, `stuck-offer`, `budget`, `depth-limit`, `superseded`, `disabled`, `rearm`, `permission-mode`, `headless`, `not-allowlisted`, `policy-unreadable` or `parent-gone`; the delivery hook writes `continue`, `continue-budget` or `continue-permission-mode` for `Stop` continuations; the Codex fork producer writes `fork`, `fork-declined`, `fork-failed`, `fork-uncertain`, `fork-superseded`, `fork-relayed` and one `fork-<code>` line per refusal before the claim (see Codex fork reply). It never contains message text.
- Codex sessions get no listener. The daemon admits CP hints and, with `wake.nativeQueue: true`, independently queues fixed native pointers for eligible exact-addressed messages. The original owner's hooks and intake consume the inbox (see [Waking Codex sessions](#waking-codex-sessions)).
- The Codex `Stop` continuation (`decision` `block`, see [Codex sessions](#codex-sessions)) goes through the same check as the Claude one: never in `bypassPermissions` (from the hook input's `permission_mode`), and within the shared budget.

#### Codex sessions

With `--runtime codex` the delivery hook serves Codex for `SessionStart`, `UserPromptSubmit` and `Stop` ([Codex hooks](https://learn.chatgpt.com/docs/hooks.md), fetched 2026-09-25). Without the flag it behaves as the Claude Code hook above; there is no auto-detection. On a machine without `node.json` it writes no file and prints nothing.

- Every call writes `codex-sessions/<session_id>.json` (`sessionId`, `cwd`, `lastSeen`, `runtime` `codex`, and `permissionMode` from the input's `permission_mode`, kept when a later input lacks it) atomically with mode `0600`. The Codex docs name no environment variable with the session id (Codex sets `CODEX_THREAD_ID` for its shell commands, which is source-defined; see [CLI](#cli)), but every hook input carries `session_id` and `cwd`. An id with characters other than letters, digits, `.`, `_` and `-` is ignored. The daemon lists sessions seen within 12 hours and removes files not seen for 7 days; historical hook metadata alone never proves a running or loaded app.
- Idle evidence (issue #408): the record also keeps `lastEvent` (`SessionStart`, `UserPromptSubmit`, `PostToolUse` or `Stop`) with its time `lastEventAt`, and `lastStopAt`, the time of the last `Stop`. An input without a known event keeps all three. The original owner's `PostToolUse` (the busy-turn hint's identity check in `node/codex-hook-owner.mts`; a subagent or other child is rejected) changes only `lastEvent` and `lastEventAt` of an existing record: it never creates one and never moves `lastSeen`, `cwd` or `permissionMode`, and it is written whatever the wake policy says. `idleEvidence()` in `node/codex-sessions.mts` reads a record as idle only when its last event is a `Stop` marked as ended (`lastStopEnded: true`) at least 90 seconds ago (a caller may pass 30 seconds to 1 hour) and the session was seen within 12 hours; a record without `lastEvent`, written by an older hook, is never idle. This is evidence, not proof: whether `Stop` fires for a cancelled turn, and whether an approval wait can be told apart, is UNKNOWN. Nothing acts on it yet; `msg sessions` and `kherep-node doctor` show it. Every hook event, the `PostToolUse` refresh included, clears `lastStopEnded`; the Codex `Stop` hook writes it after recording the `Stop`, on every exit that returns no `decision: block`, and never on the block path. A blocking `Stop` and a failed mark therefore read as not idle, and a failed mark leaves the hook output unchanged.
- Codex fork reply (issue #408, in progress): an opt-in `wake.codexFork` section, `{ "enabled": true, "sessions": ["<full thread id>"] }` with optional `platforms` (only `["darwin"]`, the default), `idleAfterSeconds` (30 to 3600, default 90) and `maxAnswerBytes` (256 to 8192, default 4096), lists the chats an ephemeral fork may answer for; ids match without case and are kept in lowercase. Absent means off; `*`, names, other platforms, values out of bounds or unknown keys turn off only this section, never the rest of `wake`. `node/codex-fork-attempts.mts` keeps one attempt per message in `codex-fork-attempts/<owner>/<messageId>.json` (exclusive create; dotfiles such as temp files or `.DS_Store` are skipped; states `launching`, `running`, `completed`, `declined`, `failed`, `uncertain`, `superseded`, forward only; at most 1,024 per owner; never deleted; a malformed record, an unexpected file or a full store fails every read closed; launching or running attempts become `uncertain` with reason `helper-exit` when the daemon starts). `node/codex-fork-admission.mts` decides one message with one reason code and spends the owner's shared turn budget only after every other guard passed; it requires this checkout's delivery hook on Codex `PostToolUse` before it trusts `Stop` evidence. Nothing changes while `wake.codexFork` is absent, except that relays made while it was present are still withdrawn when the owner reads and cleaned up after 24 hours; nothing is sent, forked or audited. With it present only `darwin` is accepted, and the answer is relayed as below.
  - The producer (`node/codex-fork-reply.mts`) runs after the CP hint admission of a wake-authorized owner that is also listed in `codexFork.sessions`, one helper at a time on the node, fenced by the service drain. Before admission it checks the `codex` on `PATH` (a native executable run directly, local route), the MCP server names (`codex mcp list`) and the feature keys (`codex features list`, cached 5 minutes per binary hash); a failure refuses without a spent turn or an attempt. Every refusal before the claim (the producer's four codes and every admission code, `cwd-refused` included) is audited once per owner, message and code as `fork-<code>` (issue #444); a failed append is not marked as noted, so the next poll that meets the same refusal writes it again once the audit file is writable. The owner's recorded `cwd` must lie inside `sessions.workspaceRoots` with `codex` in `sessions.runtimes`. The daemon applies the policy as read for each exchange round, so an opt-in or opt-out needs no restart, for the queue and the proxy send gate alike.
  - One attempt (`node/codex-fork-process.mts`): `codex app-server --listen stdio://` in the owner's working directory and its own process group, with `KHEREP_CODEX_FORK=1`; `initialize`, `thread/read` and `thread/turns/list` (newest turn `completed`) and `thread/goal/get` on the owner without loading it, a re-read of the inbox record (read meanwhile: `superseded`), `thread/fork` ephemeral and read-only at that turn with tools, hooks, goals, web search, request-user-input and the MCP servers off, `thread/goal/get` on the fork (it must answer `-32600` with exactly `ephemeral thread does not support goals: <fork id>`; anything else, `goal: null` included, is `fork-goal` with a fixed detail code), one `turn/start` with an output schema, validation, close (SIGKILL of the group after 250 ms). Every server request is refused with `-32601` and fails the attempt, as do a tool item, a goal notification, a turn the helper did not start and any notification on the owner.
  - States: `launching` (claim), `running` (fork made), then `completed` with the validated `answer`, `declined`, `failed`, `uncertain` (a turn may have run, or the close was not confirmed) or `superseded`; every `failed`, `declined` and `uncertain` carries one fixed `reason` code, a `fork-goal` failure also a fixed `detail` code, and a `running` attempt the `goalProof` `ephemeral-gate`. A JSON-RPC refusal of `initialize`, `thread/read`, `thread/turns/list` or `thread/fork` adds no persisted field (issue #477): it is recorded only as one content-free daemon log line, `kherep-node: Codex fork helper refused <method> (code <code|none>, <shape>, sha256 <12 hex>, mentions <list|none>)`, and no text of the server's message is kept anywhere. The owner goal read needs goals enabled in the identity's Codex config (the default); otherwise every attempt fails `goals-disabled`. Nothing pins a `codex` version or hash: the feature list is cached per resolved path and hash and listed again when the binary changes. Audit lines: `fork`, `fork-declined`, `fork-failed`, `fork-uncertain`, `fork-superseded` once per attempt, `fork-<code>` once per owner, message and refusal code before the claim; ids only, never text.
  - Relay (`node/codex-fork-relay.mts`, design r3): the daemon's sweep, in every poll before the inbox filter, writes one outbox record per completed attempt (`proxyOf` the original, `depth` + 1, from the owner's session, a fixed header with the three ids, then the answer) and claims `inbox/proxied/<messageId>.json`. No release is stored: the exchange sends a `proxyOf` record only when the same relay guards pass at that send (age within 24 h of `attemptedAt`, the fresh policy with opt-in, enrollment, kill switch, fingerprint, platform and answer bound, `messaging.proxy.v1` on the current connection, the original still `accepted`, the owner's recorded session idle with its task and permission guards) and the sidecar matches the attempt, relay id and fork. The relay spends no turn and starts no helper. The owner reading or answering first withdraws before any guard is consulted: exactly when nothing can have left the node, otherwise as `unconfirmed` with the record kept (never sent again) for a late status; a held record without a status after 24 h is removed and the sidecar records `unresolvedAt` (outcome unknown, a later status is acknowledged and not recorded). The withdrawal and the cleanup run in every poll for every message with a sidecar (`node/codex-fork-relay-pass.mts`), whatever the owner's session state, and do not depend on `wake.codexFork`; with the section absent no `fork-superseded` line is written. `relayedAt` and the audit line `fork-relayed` mean the Worker answered. The owner's delivery block and `msg inbox` show one line per state derived from sidecar, outbox and `sent/`; only `delivered` says not to answer again. A proxy's sent record gives the owner no failure or receipt notice.
  - Worker (`worker/src/message-proxy.mts`): a proxy is validated against the live original row only (no tombstone): any missing row or address mismatch is `proxy parent unknown`, a replied original `original already answered`, any state but `accepted` `original not waiting`, and depth as for a reply. The owner's reply and the owner node's `delivered` or `refused` report refuse every proxy of the original still queued (`superseded by the owner's reply`, `superseded: the owner read the message`); a `message.deliver` frame of a proxy re-reads its row where it is pushed (the local socket, or `NodeSession.pushFrame`) and is dropped unless still queued. A proxy already accepted at the peer stays; a refused proxy its target reports taken is audited `message.proxy.late-delivery`. `GET /api/messages` lists `proxyOf`; after the node's 24 h cleanup it, and the audit, are where a relay's outcome may still be read.
  - `KHEREP_CODEX_FORK=1`, inherited by the helper's hook children, makes the Codex delivery hook print and record nothing and skip native Queue reconciliation.
- `SessionStart` tells the session its id and the `msg send --from <session_id>` command line as developer context.
- `UserPromptSubmit` offers messages addressed to the session id or its `codex-...` name with the same semantics as for Claude Code (offer, repeat marking, refusal after 3 offers, sender failure notices and receipts; a Codex `Stop` carries no context, so receipts wait for the next prompt), as `hookSpecificOutput.additionalContext`, which Codex adds as developer context; its offers read `offeredBy` `codex-prompt`. The reply command carries `--from <session_id>`, because the CLI cannot read the id from the environment. The budget is 6 KiB: Codex spills model-visible hook output above roughly 2,500 tokens to a file, and message ids and paths tokenize densely enough that 8 KiB could cross that.
- `Stop` leaves Codex `offered` records unacknowledged. If new `accepted` messages wait and `stop_hook_active` is not true, the existing autonomous-turn budget permits a continuation with `decision: block`. Its reason is one fixed concise cue; SessionStart and UserPromptSubmit supply the trusted receive recipe. Peer text never enters that user-level prompt; it arrives as framed tool output when the continuation runs the command. Otherwise `Stop` prints nothing.
- The continuation does not require another `UserPromptSubmit`. Receiving only offers messages (`offeredBy` `receive`); the explicit owner/generation receipt ACK declares processing after complete content was returned. The full session id must have been recorded by a hook, and aliases shared by live Codex sessions are excluded. A command failure is not a receipt; an interrupted turn keeps its offers pending until the normal retry or confirmation path runs.

A blocked Stop in Hook stats is the intentional continuation above, not a hook execution failure. The Codex desktop app shows it as "Blocked · Stop · User · Feedback" with the reason beneath it, so the reason's first line starts with `Kherep message delivery (not an error):` (issue #359). Delivered means a turn carrying the message completed, or the session explicitly queued a threaded reply. It does not prove comprehension or completion of the peer request. Replied is stronger: the Worker has stored a valid response to the original sender.

The Codex installer (`codex/install.mts`) adds the three hooks to the managed block of `config.toml`, running `deliver-hook.mts --runtime codex` of the checkout or source pin it installs from. Since issue #503 the command names the stable entry point, `node --disable-warning=ExperimentalWarning <CODEX_HOME>/hooks/kherep-maestro/codex-control-plane-hook.mts deliver --runtime codex`, which runs the hook of the source named in `<CODEX_HOME>/orchestra/control-plane-source.json` with the caller's stdio, environment, working directory and exit code, and fails closed without that record; the command, and so its trust hash, stays the same across upgrades (see [Codex integration](../../docs/CODEX.md)). Codex runs non-managed hooks only after they are reviewed and trusted, and records trust against the hook's hash; review and trust them in Codex before they run. The Claude installer does the same since issue #592 with `<CLAUDE_HOME>/kherep/control-plane/claude-control-plane-hook.mts` and the pointer `<CLAUDE_HOME>/kherep/control-plane/source.json`, the same record; the Claude entry imports the hook into its own process instead of starting a second one, and its command carries no Node option.

Sending from a Codex session (issue #72) needs two things, and the installer sets up both:

- **Writable outbox.** In the `workspace-write` sandbox the node directory is outside the writable roots, so `msg send` failed with `EPERM` on the outbox and passed only on an escalated retry. The installer adds the node's `outbox/` (under `KHEREP_CONFIG_DIR` or the per-OS config directory) to `sandbox_workspace_write.writable_roots`, which the [configuration reference](https://developers.openai.com/codex/config-reference) documents as "Additional writable roots when `sandbox_mode = "workspace-write"`". Only the outbox, never the node directory with the key and `policy.json`. `msg send`, also with `--reply-to`, writes nothing else. The installer never writes a second `[sandbox_workspace_write]` table, see [Codex](../../docs/CODEX.md).
- **No approval per message.** The managed rule file `rules/kherep-control-plane.rules` in the Codex home allows `msg send`, `msg sessions`, `msg inbox` and `msg status` of the stable launcher command `node "<config dir>/bin/kherep-node.mjs"` without a prompt. Every other subcommand (`task`, `node`, `daemon`) still asks. The rule covers transport only: a peer message still cannot grant deployment, publication, deletion or permission changes.

- **Desktop app.** Measured on Windows on 2026-09-27: the Codex desktop app does not apply `writable_roots` (its threads run under a managed `:workspace`-style profile), so `msg send` in the sandbox fails with `EPERM` there. The delivery hook's context tells a Codex session to run the `msg` command on its own and request escalation on the first attempt; the rule above then runs it outside the sandbox without asking. This enables transport from a running turn; it does not establish automatic wake of an idle Desktop chat. The writable root still covers `codex exec` runs (see [Codex tasks](#codex-tasks)).

#### Waking Codex sessions

The daemon checks recorded interactive Codex sessions every two seconds. An
authorized original owner receives a bounded CP hint through its synchronous
PostToolUse hook at the next supported tool boundary in the same running turn.
The hint route is independent of the Composer's Queue/Steer preference. With
`wake.nativeQueue: true` (off by default, issue #429), a separate guarded producer
adds a native Queue pointer for exact-addressed messages. The native runtime
waits while active and starts the same loaded owner when eligible; no replacement owner, thread resume or preference change is used.
Legacy queue cards and bindings remain unchanged by Kherep at Stop.

- **Original-owner intake:** guarded CP admission publishes at most eight message ID/address pairs, TTL, policy fingerprint and immutable generation. The hook validates native owner identity without opening a transcript and returns a compact hint. Independently, and only with `wake.nativeQueue: true`, native `codex queue --thread <exact owner> --message <fixed pointer>` supplies the next eligible user turn. The runtime arbitrates active/idle eligibility; no guessed CP activity predicate or `turn/steer` call is used. Alias-only messages retain the CP route.
- **Receive and confirmation:** hint admission, Queue submission and actual owner startup are separate from delivery. Messages remain accepted until returned through original intake, then offered until explicit processing ACK. An interrupt, missing or limited Receive, hint claim or Queue ID cannot confirm remaining content. The native Queue carries no peer message body.
- **Authorization:** candidates are recorded non-task Codex sessions seen within twelve hours. Full-id wake authorization or the existing unique `codexApp` selection, alias uniqueness, kill switch, permissions, reply depth below six and TUI classification all remain. A reachable TUI is excluded from the automatic app grant; a marked owner with unknown reachability waits without admission bookkeeping. Explicit full-id authorization does not depend on that probe. Codex task threads keep their own task path.
- **Turn budget and retries:** CP hint admission and claim feed the original running turn, so they neither check nor spend the shared `wake.budget` or its spacing. Actual listener wakes and Stop continuations retain their existing budget gates. A successful hint publication suppresses readmission for ten minutes; if still accepted then, fresh authorization guards apply again. Persistence failure or contention retries the same generation on existing poll rounds while policy and TTL remain valid. Policy drift or expiry invalidates retry. Restart recovers valid CP metadata, or requires fresh admission when metadata is unavailable. None of these hint paths books a real turn. Old `.queued.json` records do not block CP hints and are not rewritten.
- **Native attempt safety:** the separate producer runs only with `wake.nativeQueue: true` and rechecks that opt-in, enrollment, policy fingerprint, exact owner, permissions, kill switch, task exclusion and current accepted message depth/address. It binds the child to the captured local Codex home and executable hashes. Before invoking the fixed command, it reserves the existing turn budget and exclusively records each message in `codex-native-attempts/<owner>/`. Repeated polls and restart cannot submit an attempted message again. Missing IDs, rejection, timeouts and partial records retain uncertainty. The store is bounded to 1,024 records per owner and fails closed when full; it does not discard history to authorize a retry. CP hints remain available when the CLI, budget or native store prevents enqueue. No legacy card/binding cleanup is introduced.
- **Confirmed pointer retirement:** normal Stop awaits public Queue list/delete/readback for exact native groups whose entire batch is delivered. Captured producer identity, local route, home, executable hashes, exact Queue ID and full input must match; enrollment is rechecked before delete. Attempts remain permanently, with separate reconciliation receipts. Late producer settlement and existing poll rounds retry bounded cleanup, including delivered pointers after wake/kill-off. Offered, partial, uncertain and foreign groups remain. Already-started turns are never interrupted; a Queue ID learned after Stop does not establish an absolute no-empty-turn guarantee.
- **Progress:** waiting intake uses `waiting/awaiting-user-turn`; publication failure uses `waiting/retry-pending`; actual offers use `waiting/awaiting-turn-confirmation`. The metadata-only audit records decisions and app grants without claiming a turn started. Claude's wake behavior is unchanged.

Genuinely closed targets retain the separate [closed-session policy](#messages-for-a-closed-session).
Source and synthetic hook/CLI tests do not prove installation, hook trust or actual
Desktop processing. Owner-turn acceptance is tracked in
[issue #374](https://github.com/cfaysal/kherep/issues/374).

## Tasks

A task is an instruction that a node runs as a Claude Code background session (item 5, operator decisions of 2026-09-25) or, with runtime `codex`, as a `codex exec` run (issue #63, see [Codex tasks](#codex-tasks)). A node runs Codex tasks only when its policy lists `codex` in `sessions.runtimes`; otherwise it refuses them with the reason `runtime codex is not supported on this node yet`.

- **Who creates tasks.** The operator, through `POST /api/tasks` behind Access. A session may request one with `task new` only on the operator's explicit directive (see [Delegated tasks](#delegated-tasks)). Nothing else starts, stops or continues a session: nodes cannot send commands, the `commands` API refuses session commands, and a peer message starts nothing.
- **Node selection.** With `requirements.node` (a node id, issue #74) the Worker takes exactly that node when it is online, not revoked and fits every other requirement below, and otherwise refuses with the reason (`unknown node`, `is not online`, `does not advertise ...`, `runs <os>, not <os>`, `has no <runtime> CLI runtime`); it never falls back to another node. Without it the Worker takes online, non-revoked nodes that advertise `sessions.v1`, list the runtime (`claude` or `codex`, default `claude`) as a CLI runtime and match `requirements.os` (the node's `os` fact, for example `win32`, `darwin`, `linux`) and every `requirements.capabilities` entry; among them the node with the fewest active tasks, by name on a tie. Without one it answers 409 with the reason and audits `task.refuse`. It stores the task as `dispatched` and queues `session.start` with `taskId`, `runtime`, `name` (`task-<first 8 of taskId>`), `prompt` (the task text), `permissionMode` (default `auto`; `auto`, `default` or `acceptEdits`, never `bypassPermissions`), `requirements.cwd` as `cwd` and, when the task has one, `label`. `POST /api/tasks` takes an optional `label`; the Registry keeps it in the `tasks` table (a column added on start) and the node in `tasks/<taskId>.json`.
- **Start.** The node checks its `sessions` policy, the runtime, the permission mode, its limits and the working directory, then runs `claude --bg --name task-<8> --permission-mode <mode> "<framed prompt>"` in that directory (also for a task with a label: the node maps the session by that name until it knows the short id, and the Worker and the node recognise a task session by it, while a label is shared by every intercom session from one sender; the label is shown only in the directory), with the same executable lookup as the session listing. The prompt is one argument of a process started without a shell. A Windows npm install puts a `claude.cmd` shim on `PATH`; when the native `claude.exe` the package ships sits next to it (`node_modules/@anthropic-ai/claude-code/bin/claude.exe`), the node runs that executable directly. A shim without it needs `cmd.exe`, which cannot carry arbitrary text safely, so a start or continue through such a shim fails with that reason. `--bg` prints `backgrounded · <short id> · <name>` (the [agent view documentation](https://code.claude.com/docs/en/agent-view), fetched 2026-09-25); the node records the short id and maps the full session id from `claude agents --json --all` (by that short id, else by name) into `tasks/<taskId>.json` with `name`, `cwd`, `permissionMode`, `startedAt`, `deadline` and `state`, and reports `started`. A refusal or a CLI error, for example a CLI that is not signed in, reports `failed` with the CLI's own message (at most 256 characters), never the command line. The task session's environment is the daemon's, with the directory of the Node executable the daemon runs under (`process.execPath`) put first on `PATH` unless it already is (issue #79; Windows keeps the key's casing, for example `Path`), because a background session on macOS had no `node` on its `PATH`. It leaves out the daemon's own `CLAUDE_CODE_ENTRYPOINT` and `CLAUDECODE`, so a daemon started from a Claude Code session or a `claude -p` run does not pass them on (issue #235).
- **Runtime readiness.** Issue #197: `claude auth status` reported `loggedIn: true` for an expired login while every call returned 401, so the node checks with a real minimal call whether a runtime can run a turn. Claude Code: `claude -p --safe-mode --no-session-persistence --strict-mcp-config --tools "" --output-format json --system-prompt "Reply with OK." OK`, ready only for a result with `is_error` false ([CLI reference](https://code.claude.com/docs/en/cli-reference), [headless](https://code.claude.com/docs/en/headless), fetched 2026-10-04): `--safe-mode` loads no CLAUDE.md, hooks, plugins or MCP servers, so no Kherep hook sees the probe; no tools and a one-line system prompt keep the request minimal (token count not measured); an expired login "stops locally ... before it reaches the API" ([errors](https://code.claude.com/docs/en/errors#login-expired)). Codex: `codex -c features.hooks=false -c features.codex_hooks=false <MCP overrides> exec --json --ephemeral --skip-git-repo-check --sandbox read-only -C <temp dir> -` with `Reply with OK.` on stdin, ready only after `turn.completed`. It loads the user's `config.toml` as a real run does (model, provider, authentication) but runs no hooks: an installed node's Stop, SessionStart and UserPromptSubmit hooks would dispatch observation work, write memory and outlast the timeout. `codex features list` (CLI 0.160.0, measured 2026-10-04) shows `hooks stable true`, and `false` with `-c features.hooks=false`; `features.codex_hooks` is accepted there without effect and kept for older CLIs. Its MCP servers are disabled with the same `-c mcp_servers.<name>.enabled=false` overrides as intercom runs (**Intercom runs: no MCP servers** below); `--ephemeral` persists no session files. Should a delivery hook still record the probe's thread as a Codex session, the daemon removes that one record after the probe, also after a timeout or an error. Both run in the temp directory without a shell, killed with their process tree after 45 seconds; on macOS and Linux the process group gets SIGTERM first and SIGKILL 5 seconds later (issue #420). The daemon probes each runtime in `sessions.runtimes` once at its start, unless the previous daemon's `daemon.json` holds a ready verdict for it younger than 10 minutes and no interrupted Claude probe is on record; that verdict is then used as the first one (issue #420). A stopping daemon starts no probe and waits for the one in flight. Afterwards a verdict is used stale while it revalidates: a caller gets the last verdict at once, and one older than 10 minutes (ready) or 2 minutes (otherwise) starts a probe in the background. The 60-second session round also revalidates a runtime that is not ready, at most every 2 minutes, so a re-login is noticed and advertised without a run; a ready runtime is probed only when a run needs it. There is no other periodic probe, and concurrent callers share one probe. Only a runtime without any verdict yet makes a task start or continue wait; the daemon waits for that first probe outside its frame lane, so inbound messages, receipts and native MCP intent acknowledgements are handled meanwhile, and commands keep their order on a lane of their own (`node/readiness-lane.mts`). The verdict is `ready`, or not ready with the cause `sign-in required` (the CLI's error names a login, an expiry, 401 or authentication), `probe timed out` or `probe failed`; the daemon log names the cause and the CLI's last line, redacted as for Codex stderr below. Only `sign-in required` blocks: a task for that runtime reports `failed` with the fixed reason `target runtime <runtime> not ready (sign-in required)` and starts nothing (no record, no slot, no start counted). A probe that timed out or failed otherwise proves nothing about the run (a network blip, a CLI too old for a probe flag), and a task start is not retried by the Worker, so the task runs as before: the CLI's own error and the bound below still apply. Messages wait instead (`retry-pending`) until a probe decides. The node advertises `runtime.claude.ready.v1` or `runtime.codex.ready.v1` while the last verdict of that enabled runtime is ready, and registers again when it changes; `requirements.capabilities` may name one. A Worker keeps capabilities as opaque strings of at most 64 characters, so an older Worker accepts them.
- **No progress after start.** Every run the node starts (task start and continue, the intercom starts and resumes of [messages for a closed session](#messages-for-a-closed-session), the Codex message resume) records `awaitingProgressSince`. The watch round clears it at the first progress of the run's turn. Claude: the session `done`, `working` 30 seconds or more after the start (a turn that fails at once may read `working` for a moment), or `blocked` with `waitingFor` `permission prompt`, `input needed` or `sandbox request`; `blocked` without such a prompt, which the [agent view](https://code.claude.com/docs/en/agent-view) documents for "an error only you can clear such as an expired login", and any state outside the documented five (for example `idle`) are no progress. Codex: an `item.*` event or `turn.completed` in the run's events. A run without progress 10 minutes after its start is stopped (`claude stop <short id>`; the Codex process tree as at the max runtime) and reported `failed` with `no progress after start`, and the runtime's verdict ages out, so the next caller starts a new probe. A failed listing decides nothing.
- **Framed prompt.** `Task <taskId> from the operator via the Kherep Control Plane: <text>`, then how to report (`<cli> task done <taskId> --summary "..."`) and that `<cli> msg` carries the task id automatically. On a host whose managed launcher resolves (a valid service receipt, its pin and the pin's CLI present, the launcher file in place), `<cli>` is the stable command `node "<config directory>/bin/kherep-node.mjs"` (issue #436); the daemon does not check the launcher's bytes, `kherep-node doctor` does. Otherwise `<cli>` names this CLI by absolute path in single quotes, which keep it literal. On macOS and Linux the daemon's own Node goes by absolute path too, so a command needs no `PATH` lookup: `'/opt/homebrew/bin/node' '<repo>/modules/control-plane/node/cli.mts'`. On Windows a session may run the command through Git Bash (the Bash tool of Claude Code) or PowerShell (Codex), so the form works in both: bare `node`, which the task's `PATH` resolves to the daemon's Node first, and the CLI path with forward slashes, `node 'C:/<repo>/modules/control-plane/node/cli.mts'`. No quoting of a single quote works in both shells, so on Windows a CLI path containing one refuses the task start with that reason. The text is operator content given through Access, not peer content.
- **Watch.** With every 60-second session check the daemon runs `claude agents --json --all` while a task is active and maps its documented `state`: `working` to `running`, `blocked` to `needs-input`, `done`, `failed` and `stopped` as they are. Each change is reported once with `task.report`. A failed listing decides nothing. After `maxRuntimeMinutes` the node runs `claude stop <short id>` and reports `stopped`, reason `max runtime reached`.
- **Stop and continue.** `POST /api/tasks/{id}/stop` runs `claude stop <short id>` (reason `stopped by the operator`); `POST /api/tasks/{id}/continue` runs `claude --resume <sessionId> --bg --permission-mode <mode> "<follow-up>"` for a task in state `needs-input`, `done`, `failed` or `stopped`, with a new runtime deadline. A node acts only on tasks it started itself. Claude Code may continue a session under a new id; the next watch round maps it. The local `task` CLI has no stop command: it only writes session-side files and has no authoritative daemon transport, so exact-id stop remains the operator API path.
- **Reports.** `task.report` (node to Worker) carries `taskId`, `state` (`started`, `running`, `needs-input`, `done`, `failed`, `stopped`), optional `sessionId`, `reason` (at most 256 characters) and `summary` (at most 2048). The Worker accepts it only from the node the task was dispatched to.
- **Limits.** Claude and Codex tasks share the node's limits: `maxConcurrent` and `maxStartsPerDay` count both.
- **Retention and audit.** The Registry keeps the task text for `GET /api/tasks/{id}`; the task list and the audit table never contain it, nor a continue prompt. Every create, refusal, report, state change, stop and continue is audited with the task id.


#### Inspect one already classified safe reply

When a trusted external source has already identified a safe incoming reply's
exact ID, owner, raw sender tuple, exact original sent destination, original sent root
and text SHA-256, inspect only
that record:

```sh
node "<config directory>/bin/kherep-node.mjs" msg inbox --message-id <incoming-UUID> --from <owner-UUID> --expect-node <sender-node-UUID> --expect-session <exact-raw-sender-ref> --expect-target-session <exact-raw-target-ref> --expect-reply-to <original-sent-UUID> --expect-text-sha256 <safe-text-SHA256>
```

The stable launcher follows the installed service pin. To use this read-only
operation from a reviewed, clean committed checkout before upgrading that pin,
invoke the supported source CLI with the same selectors:

```sh
node "<clean checkout>/modules/control-plane/node/cli.mts" msg inbox --message-id <incoming-UUID> --from <owner-UUID> --expect-node <sender-node-UUID> --expect-session <exact-raw-sender-ref> --expect-target-session <exact-raw-target-ref> --expect-reply-to <original-sent-UUID> --expect-text-sha256 <safe-text-SHA256>
```

Verify that checkout's commit and reader bytes before use. This invocation
does not start or restart the daemon, change its pin, or run its inbox index.

All seven selectors are mandatory. Message, owner and node IDs use full lowercase
UUIDs, and the text hash is a lowercase 64-character SHA-256. `--expect-session`
is the exact raw sender reference; `--expect-target-session` is the exact original
sent destination reference. Both accept a session name or UUID. They bind the selection; they do not prove the content is
public or safe. Sender identity or an original public request does not classify
its reply. Both raw references and their association with the chosen peer must
come from trusted external evidence. The command compares them literally, never
resolves aliases, and does not attest a canonical peer UUID from names. A
`msg send --reply-to` destination can retain the original peer's raw sender name.
Codex normally supplies the same full UUID for both selectors. If the reply ID or safe hash is unknown,
this path is unavailable.
Do not discover them by scanning inbox bodies or falling back to `--all`.

Before any incoming body access, the command rejects malformed, incomplete,
duplicate or mixed options, including selector spellings after `--`, verifies the existing exact caller identity and
reads only the explicitly selected authored-safe sent root. That root must
belong to the exact owner and store the expected exact destination tuple. A sent
message may itself be an ordinary threaded reply; its optional parent UUID is
validated without reading or following that ancestor. Proxy parents are refused. Under
the selected record's existing lock, it then reads only that bounded regular
nonsymlink, single-link incoming file. The stored envelope is checked **after**
this preauthorized file read, not independently attested before it. Current
message ID, exact owner, sender node/session, reply root and text hash must all
match; proxy and forwarded records are refused.

Success writes one JSON object with `messageId`, `from`, `toSession`, `inReplyTo`,
`text`, `state`, `createdAt` and `receivedAt`, bounded to 128 KiB. Inspection does
not offer, receive, readdress or confirm the message and leaves its record bytes
unchanged. Errors are fixed `exact-inbox-*` codes with no record content, paths,
notices or directory rendering; failures never mean an empty inbox. Legacy
broad inspection and `msg status` retain their existing behavior; Codex receive uses the [explicit receipt contract](CODEX-RECEIPTS.md).


### Session policy

Sessions are off unless `policy.json` has a `sessions` section with `enabled` `true` and at least one workspace root:

```json
{
  "version": 1,
  "allowedCommands": ["node.status", "runtime.list", "session.list"],
  "sessions": {
    "enabled": true,
    "workspaceRoots": ["D:/work"],
    "runtimes": ["claude"],
    "permissionModes": ["auto", "default", "acceptEdits"],
    "defaultPermissionMode": "auto",
    "maxConcurrent": 3,
    "maxStartsPerDay": 10,
    "maxRuntimeMinutes": 120,
    "delegate": { "request": false, "accept": false }
  }
}
```

- Every field but `enabled` and `workspaceRoots` is optional with the values shown. The limits are the operator's caps: a smaller positive integer narrows them, a larger one counts as the cap. `runtimes` defaults to `["claude"]`; listing `codex` lets the node run Codex tasks, an operator decision per node. Unknown runtimes and `bypassPermissions` in `permissionModes` are dropped. A malformed section (wrong types, a relative workspace root, a limit that is not a positive integer, a default mode that is not allowed) turns sessions and delegation off; the rest of the policy stays in force.
- The working directory is `requirements.cwd` or the first workspace root. It must exist and lie inside a workspace root after resolving symbolic links and junctions on both.
- Limits per node: at most `maxConcurrent` task sessions in `started`, `running` or `needs-input`, at most `maxStartsPerDay` starts per rolling 24 hours (every start that reached the CLI counts), and `maxRuntimeMinutes` per run.
- The node advertises `sessions.v1` only when sessions are enabled, `sessions.delegate.accept.v1` when `delegate.accept` is also true, and `sessions.delegate.request.v1` when `delegate.request` is true.
- Prerequisite: the Claude CLI (and, for Codex tasks, the Codex CLI) must be installed and signed in for the account the daemon runs as; task sessions use that account's stored credentials. The [readiness probe](#tasks) checks this with a real call; a node that is not signed in refuses runs with `target runtime <runtime> not ready (sign-in required)`.

### Session tools for tasks

```sh
node modules/control-plane/node/cli.mts task done <taskId> [--summary <text>]
node modules/control-plane/node/cli.mts task show [<taskId or requestId>]
node modules/control-plane/node/cli.mts task list
node modules/control-plane/node/cli.mts task new --title <title> --directive "<the operator's instruction, verbatim>" [--runtime claude|codex] [--os <os>] [--cwd <dir>] [--capability <name>]... -- <task text>
```

- `task list`, and `task show` without an id, label local records as `execution` and cached outgoing records as `request-dispatch`. `task show <id>` first resolves an exact local execution, then an exact request id, then an exact reverse match from a dispatched task id. Multiple reverse matches fail as ambiguous; invalid and unknown ids fail explicitly.
- Task detail is a metadata-only local projection. It excludes task text, directive, title and summary. Local Claude tasks include the task-specific `claude logs <short id>` inspection command. Local Codex tasks list the latest run's events, last-message, stderr and exit paths with existence flags, without reading their contents. A cached remote request shows its requested and dispatched target separately and reports live execution and desktop chat visibility as `unknown`; this cache is not a live status probe. Refused requests retain their refusal reason. A `dispatched` request carries `dispatchMeaning`: the Worker queued the start, the target has not acknowledged it. The newest settled `task status` answer for the task appears as `lastStatus` (issue #240).
- `task done` writes a `task.report` `done` with the summary to `task-reports/`, which the daemon sends in its 2-second exchange round. From a session it works only for the task that session was started for (`CLAUDE_CODE_SESSION_ID`, or the Codex session the runtime rule of [CLI](#cli) names); an environment whose session that rule refuses, such as an undecidable nesting, reports nothing (issue #471). The Claude process keeps running after it, so the local record stays counted for `maxConcurrent` and watched for `maxRuntimeMinutes` until `claude agents --json --all` shows the session `done`, `stopped`, `failed` or gone; a deadline stop then ends the process without changing the reported `done`.
- `msg send` from a session started for a task adds that `taskId` to the message, found in `tasks/` by `CLAUDE_CODE_SESSION_ID` (or the session's name); `msg send --reply-to` keeps the `taskId` of the message it answers. The Worker accepts a `taskId` only when the sending or the target node runs that task.
- Task grant: the wake listener also wakes a session this node started for a task (sessions enabled) for a message whose `taskId` is that task, even when the `wake` allowlist does not name the session or waking is turned off. An intercom session the node started itself for a closed session's messages (task record `local` `intercom`, see [messages for a closed session](#messages-for-a-closed-session)) is also woken for the messages of the session it answers (its `requestedBy`), which carry no task id (issue #105); the Codex exchange round resumes such an ended Codex session under the same grant. The budget (by default 20 per rolling hour, 100 per rolling day, 30 s spacing; `wake.budget`), the `bypassPermissions` exclusion, the reply-depth limit and the kill switch still apply. The grant follows the session id the node records for the task. The node writes the task record before it runs `claude --bg` or `claude --resume <id> --bg`, with `mappingPendingSince`, and clears that field once `claude agents --json --all` lists the session's id (right after the run, else in the watch round). A session can arm its listener before that mapping lands, and after a resume Claude Code may continue it as a copy under a new id (issue #109). So a listener without a grant or allowlist entry does not exit while an active task or intercom record of this node in the same working directory has had `mappingPendingSince` for at most 2 minutes. It looks the grant up again at each poll, by session id only, and wakes as usual once the node has recorded its id. The pending mapping alone never grants anything: when the window passes, the mapping names another session, or the listener's timeout comes, it exits with one `not-allowlisted` audit.

### Codex tasks

A task with `requirements.runtime` `codex` (issue #63) runs as `codex exec` on a node whose policy lists `codex` in `sessions.runtimes`. Admission, limits and the working directory rule are the same as for Claude tasks. The flags below follow `codex exec --help` and `codex exec resume --help`; the Windows `codex exec` sandbox was measured with CLI 0.157.1 as described below, while the resume path was not remeasured for this change.

- **Start.** The daemon runs `codex exec --json --skip-git-repo-check -C <cwd> --sandbox <sandbox> --add-dir <outbox> -o <last message file> -` in `<cwd>`, detached in its own process group (except a Codex intercom run on Windows, see **Windows: intercom runs** below; on Windows through a windowless wrapper, see **Windows: operator tasks**). The framed prompt goes in on stdin (`-`: "instructions are read from stdin"), and stdin is closed right after it, so `codex exec` does not wait for more input and the task text never shows in the process list. The events go to `codex-tasks/<taskId>/events.jsonl` in the node directory, stderr to `stderr.log` there, and `-o` writes `last-message.txt`. The node records the pid and the process start time, waits up to 15 seconds for the first `thread.started` event and records its `thread_id` as the task's `sessionId`, then reports `started`. A thread id that shows up later is reported by the next watch round.
- **Git check.** `--skip-git-repo-check` skips only Codex's check that the working directory is a trusted Git repository, not the sandbox; the node already confines the working directory to its workspace roots, which need not be repositories. Without it such a task fails at once with `Not inside a trusted directory and --skip-git-repo-check was not specified.` (measured on macOS).
- **Framed prompt.** As for Claude tasks, except the closing instruction: a Codex task ends its turn with a short summary, which is reported as the task's result, instead of running `task done`.
- **Sandbox.** `codex exec` cannot ask for approval, so the permission mode maps to a sandbox: `auto` and `acceptEdits` to `workspace-write`, `default` to `read-only`. The node never passes `--dangerously-bypass-approvals-and-sandbox`, `--dangerously-bypass-hook-trust` or `--approve-for-me`, and refuses a command line that contains one.
- **Watch.** With every 60-second session check the node checks each active Codex task's process: while the daemon still holds the child it started (its pid cannot be reused before it is reaped, and the holder is compared again after every awaited read), otherwise by pid and recorded start time. A start time that could not be read at the start is read again while the child is held. A failed read decides nothing. The start-time and process-tree reads are awaited child processes (issue #473): while PowerShell or `ps` runs, the daemon keeps storing incoming messages; a read over 2 seconds is logged as `child process process-start took <s> s` (or `process-relations`). A run whose `exit.json` exists has ended without any read: the daemon writes that file only when it sees the exit of a process it started, and removes it before each run (issue #121). On Windows the start time comes from `try { (Get-Process -Id <pid> -ErrorAction Stop).StartTime.ToFileTimeUtc() } catch [Microsoft.PowerShell.Commands.ProcessCommandException] { exit 0 }`: no output and exit 0 means no such process, any other error (for example a start time that reads as null) exits non-zero and counts as a failed read. The earlier form with `-ErrorAction SilentlyContinue` exited 1 for an ended pid (measured 2026-09-28 with Windows PowerShell 5.1 `powershell.exe`), so finished runs stayed `started`. When the process has ended, the task is `done` if the events contain `turn.completed` and the exit code was 0 (or the daemon did not see the exit), with the last message as the summary (at most 2048 characters); otherwise `failed` with the `turn.failed` or `error` message, or the exit code followed by codex's last non-empty stderr line (API keys, bearer tokens, JWTs, URL user info and URL query strings redacted, control characters removed, at most 200 characters, dropped when it quotes the framed prompt, which names Kherep in any case), never the prompt. A run without start time, held child or recorded exit (after a daemon restart) is reported `failed` with the reason `process identity unknown` instead of keeping its slot; its process, if it still runs, is not stopped. Issue #233: while a run lives, each round also records its descendant processes in the task record (pid and start identity, at most 32, closest to the root first), from one process listing (`ps`, on Windows one PowerShell Toolhelp snapshot) and a start read only for a pid not recorded yet; a root that ended during the listing leaves the record unchanged. When a run's root ends and it settles `failed` (for example `codex ended by SIGKILL`), or a stop finds `exit.json`, every recorded descendant that still has its recorded start identity gets SIGTERM and, after up to 5 seconds, SIGKILL by its own pid (`taskkill /PID <pid>`, `/F` for SIGKILL, on Windows), off the daemon's frame lane, and the node logs which pids it ended; a reused pid is never signalled. Shell commands run in their own process group and are re-parented to init when the root crashes, so neither a group signal nor `taskkill /T` reaches them. A run that settles `done` keeps what it started. After `maxRuntimeMinutes` the node stops the process and reports `stopped`, reason `max runtime reached`; a run with `exit.json` is settled from its outcome instead, even past the deadline, and so is a run whose root is no longer the recorded process (ended, or its pid reused), whose recorded descendants are then ended as above (issue #544). The run is measured before the deadline stop, so a run that ended on its own past the deadline is reported from its outcome, not as `stopped` at the max runtime, and the node logs `its root (pid <pid>) is no longer the recorded process; settled from its outcome`. The process that holds a reused pid is read once, for its start time, and never signalled.
- **Stop.** `POST /api/tasks/{id}/stop` first records durable operator-stop intent, then signals only the recorded process identity. On macOS and Linux it snapshots the process group tree with each pid's start identity; on Windows it verifies the recorded root start identity and uses synchronous `taskkill /T`. The start-time and tree reads of a stop and of its waits are awaited child processes and do not hold up message intake (issue #473); each signal still follows the read of its pid's start directly, and a root the daemon held when the stop began gets a signal, or is forced after a timeout, only while that same child is still held after the read. It sends SIGTERM, waits up to 5 seconds for every captured identity to end, then sends SIGKILL (`taskkill /T /F` on Windows) and waits again. The group or tree signal goes out only while the root still has its captured start identity. Issue #231: Codex runs shell commands in their own process group, which the group signal misses, and the root can end before them, which `taskkill /T` cannot follow; so after each group signal every captured descendant that still has its captured start identity also gets the same signal by its own pid (`kill(pid)`; `taskkill /PID <pid>`, with `/F` for SIGKILL, on Windows). A pid whose start identity changed is never signalled. A root that has lost its recorded start identity before the capture has no tree of the run: nothing under that pid is listed, read or signalled, and the stop records the task `stopped`; the run's recorded descendants are not ended by that stop (issue #544). A root the daemon holds is the run's process whatever its start reads, and is not treated so. A failed SIGTERM send does not end the stop early; a stop whose processes still run after SIGKILL names why (root ended or reused, failed SIGKILL sends). Only confirmed termination, a changed pid start identity, or an `exit.json` advances the task to `stopped`; an unreadable identity, signal error or surviving process tree returns an error and emits no stopped report. Issue #221: on Windows a process-tree query that hits its 10 second limit runs once more; when a `ps` or PowerShell helper still times out, the stop forces the tree of the root if that root still has its recorded start identity (SIGKILL, `taskkill /T /F` on Windows) and returns the error anyway, so the tree does not keep running and no unconfirmed stop is reported; a later watch round settles the task as an ended run. The watch retries a pending operator stop. A task that reported `done`, and a run started for peer messages, keep their reported state and send no report. The durable intent prevents peer-message and closed-session automation from resuming or replacing that session; an explicit continue clears it. A stop of a run whose root already ended (its `exit.json` exists) captures nothing; it ends the run's recorded descendants as described under **Watch** (issue #233).
- **Continue.** For an ended run with a known thread, explicit continue clears any durable operator-stop intent and runs `codex exec resume --json --skip-git-repo-check -c sandbox_mode="<sandbox>" -c sandbox_workspace_write.writable_roots=["<outbox>"] -o <last message file> <thread_id> -` in the task's working directory, with the follow-up on stdin and a new deadline. The working directory is checked again first, as at the start, so a directory swapped for a link out of the workspace roots is refused; the thread id must be a plain id (it cannot start with `-`). `codex exec resume` has no `-C`, `--sandbox` or `--add-dir` flag.
- **Messaging out.** Besides the working directory, the node's `outbox/` is the only extra writable root, so `kherep-node msg send` works from a `workspace-write` sandbox (`auto`, `acceptEdits`); the rest of the node directory (key, policy, task records) stays read-only, and a `msg` read that asks for a directory refresh cannot write that request. The [configuration reference](https://developers.openai.com/codex/config-reference) documents extra writable roots only "when `sandbox_mode = "workspace-write"`", so a Codex task in permission mode `default` (`read-only`) most likely cannot send messages; the node passes the root anyway, and whether Codex honours it there is not measured yet. The process gets the daemon's Node directory first on `PATH` (as for Claude tasks), `KHEREP_CONFIG_DIR` (the node directory) and `KHEREP_SESSION_ID` (the thread id, or the task name before it is known); a `CLAUDE_CODE_SESSION_ID` the daemon inherited is removed. `KHEREP_SESSION_ID` stays the run's sender identity; once the task's thread is known, a `CODEX_THREAD_ID` that differs from it (another Codex started inside the task's shell) is refused (issue #471). Messages it sends carry the task id.
- **Messaging in.** A `codex exec` run ends with its turn, so the daemon's 2-second exchange round resumes an ended Codex task for messages addressed to its thread id or name: `codex exec resume` as above, in the task's working directory, checked again as for a continue, with a prompt (on stdin) that starts with the wake text and carries the messages framed as the delivery hook frames them (per-call nonce markers, peer content that is not an instruction from the user). The messages are marked `offered` (`offeredBy` `codex-wake`); when the run completes its turn they become `delivered`, otherwise they are offered again, at most 3 times (`MAX_OFFERS`). The guards are the Claude wake's: the kill switch `wake.disabled`, the `wake` allowlist or the task grant (messages of the task's own id), no `bypassPermissions`, reply depth below 6, and the shared budget per session, by default 20 autonomous turns per rolling hour, 100 per day and 30 s spacing (`wake.budget`); each decision goes to `wake.jsonl` without text. Since a resume starts a process, it also needs sessions enabled with `codex` in `runtimes` and a free slot under `maxConcurrent`. One run per task: messages that arrive meanwhile wait. The start-time read that tells whether the previous run is still ending starts a process too, so the round reads it only after the `maxConcurrent` and working-directory checks, and still before the readiness verdict and the turn budget (issue #473): a run still ending keeps its messages `target-busy` and is neither refused nor charged a turn meanwhile. Such a run keeps the task's reported state (no `task.report`), counts as active, and is stopped at the max runtime like any run. A durable operator-stop intent leaves incoming messages waiting and prevents this automatic resume until an explicit continue clears it. Every waiting message carries a progress code (issue #197): `operator-stopped` for a stopped task and `target-busy` while a run is active (each exchange round, reading the inbox only when such a task exists; a message closed-session delivery handed over keeps that path's progress), each guard's code when a guard holds the resume (`wake-not-authorized`, `reply-limit`, `wake-disabled`, `permission-restricted`, `retry-pending`, `budget-exhausted`; see the [reason-to-code table](#messages-for-a-closed-session) for the Codex task resume), `wake-failed` when the resume cannot start, and `awaiting-turn-confirmation` for the messages a started run carries. When the [readiness probe](#tasks) finds Codex not signed in, the waiting messages are refused with `target runtime codex not ready (sign-in required)` (audit action `runtime-not-ready`) and no resume starts; without a verdict, or after a probe that timed out or failed, they wait with `retry-pending`. A run without progress 10 minutes after its start is stopped; its messages get `wake-failed` and are offered again within `MAX_OFFERS`, after a new probe.
- **Windows.** An npm install puts a `codex.cmd` shim on `PATH`, and `cmd.exe` cannot carry arbitrary text safely. The shim only runs `node "%dp0%\node_modules\@openai\codex\bin\codex.js" %*` (measured on a Windows node), so the node runs that launcher itself with its own Node executable and without a shell. The launcher's setup is kept: it finds the native `codex.exe` of the platform package (`@openai/codex-win32-<arch>`) and sets `CODEX_MANAGED_PACKAGE_ROOT` and `CODEX_MANAGED_BY_NPM` (read from `bin/codex.js` of `@openai/codex` 0.152.1). A shim without the launcher next to it, and any other `.cmd` or `.bat`, is refused. The launcher's Node then runs codex as its child, and for an operator task both run under the windowless wrapper (**Windows: operator tasks**): stop and the deadline end the whole tree (`taskkill /T`, then `/T /F`; the process group on macOS and Linux).

### Delegated tasks

A Maestro session may ask for a task with `task new`, which writes `task-requests/<requestId>.json`; the daemon sends it as `task.request` with `title`, `text`, `requirements`, `directive` and `requestedBy` (this session's name or id), and records the Worker's answer (`task.request.result`: `dispatched` with `taskId` and `nodeId`, or `refused` with a reason) in the same file.

Codex Desktop callers without a session environment may supply
`task new --from <full-codex-session-id>`. The ID must have a complete, matching
Codex hook record seen within 12 hours. Unknown IDs, short aliases, unreadable or
malformed records and conflicts with an existing runtime session are refused.
Every present `CLAUDE_CODE_SESSION_ID` and `KHEREP_SESSION_ID` marker must match, and so must the
session the runtime identity names (issue #471); one matching marker cannot hide another conflicting or empty
marker. A `CLAUDE_CODE_SESSION_ID` beside `CODEX_THREAD_ID` is no marker unless the nesting rule of
[CLI](#cli) decides Claude, so a Codex thread started from a Claude Code tool may pass its own recorded id.
The request retains the full ID. This option does not enable delegation or
permit a task session to request another task.

Supply `task new --node <full-target-node-id>` to bind a request to one node.
The Worker then applies runtime, OS and capability requirements to that exact
node; it cannot select another eligible node as a fallback.

- Both nodes opt in: the requesting node needs `sessions.delegate.request: true`, the target node `sessions.delegate.accept: true` (with sessions enabled). Both default to false. The requesting node checks before it sends; the Worker checks the capability again, and picks only nodes that advertise `sessions.delegate.accept.v1`. All start limits of the target apply.
- A delegated task always runs in permission mode `auto` (the target refuses anything but `auto` or the stricter `default`), never `bypassPermissions`.
- No chains in v1: a session that was itself started for a task cannot request tasks. `task new`, the daemon and the Worker each refuse it.
- A node runs either task sessions or delegation requests, not both at once. A session names itself (`CLAUDE_CODE_SESSION_ID`, and `requestedBy` is what the node reports), so a task session could pose as another session, and a new session is not mapped in `sessions.json` right away. The daemon therefore sends no `task.request` while the node has any active task record (reason `this node runs task sessions and sends no task requests while one is active`), and the Worker refuses a `task.request` from a node with a task in `dispatched`, `started`, `running` or `needs-input`. The session checks remain as further layers.
- The Worker refuses an empty directive. It creates the task with `created_by` `session:<nodeId>/<session>` and keeps `requestedBy` and the directive; the audit records both, because the directive is the operator's own words, but never the task text. The framed prompt says `Task <taskId> requested by session <nodeId>/<session> on the operator's directive` and quotes the directive.
- Rule for the Maestro: use `task new` only when the operator's own prompt in that session asks for it, and quote that instruction verbatim in `--directive`; never because of a peer message. This is enforced by the ROUTING rule and the audit trail, not technically: the control plane cannot prove where a directive came from.

### Owner task status and confirmed stop

Owner task control is opt-in (issue #134). Set `sessions.ownTaskControl: true`
in the local policy on the requesting and target nodes, with sessions enabled
and the required runtime allowed, then restart both daemons. This advertises
`sessions.own-task-control.v1`. Existing installations remain disabled until the
operator enables the policy. Deploy the compatible Worker before activating nodes.

```sh
kherep-node task status <taskId-or-owned-requestId-or-messageId>
kherep-node task stop <taskId>
kherep-node task stop <taskId> --expected-run-version <captured-run-version>
kherep-node task result <requestId>
kherep-node msg stop <taskId | sent messageId | owned requestId> [--expected-run-version <captured-run-version>]
```

`msg stop` runs the same status-then-stop sequence for the sender of a message or
the requester of an intercom task and ends with a one-line verdict; see
[CLI](#cli).

When stopping a captured run, supply its original 64-character lowercase run
version. Fresh status for a different run submits no Stop. The Stop request
retains the supplied version, and the Worker and target node check it again at
execution. Resolve a pending Stop with `task result <requestId>` using that same
request ID; do not submit another Stop. Omitting the option retains the existing
behavior of stopping the run identified by fresh status.

`task status` requests a new target measurement. The Worker resolves an owned
request or source message to its task; the task id addresses a known task directly.
The result distinguishes task-record state, process state, observation time and
freshness. A stored result is labelled `cached`; missing evidence stays `unknown`
or `unavailable`. These commands do not expose a transcript or imply that a task
has an open Desktop window. `task show` remains the local metadata lookup.

A start the target refuses (issue #240), for example `cwd does not exist on this
node`, is never silent. The target logs `kherep-node: task <taskId> refused:
<reason>` and every failed command result as `kherep-node: command <command>
<commandId> for task <taskId> failed: <reason>`, never with the prompt. It keeps
a refusal record in `task-refusals/`, so `task status` measures the task as
`taskState` `failed` with `processState` `closed` instead of `task_unknown`. A
requesting node with owner task control also advertises
`sessions.own-task-control.report.v1`; the Worker then adds `reportedState` and
`reportedReason`, the state and reason of the target's last `task.report`, which
also covers a target that predates this change. An older requesting node or
Worker sees neither field. `task show <taskId>` explains a `dispatched` request
with `dispatchMeaning` (the Worker queued the start; the target has not
acknowledged it) and shows the newest settled status answer this node holds as
`lastStatus`.

`task stop` first obtains status and then submits a stop for that exact run.
Confirmed remote stop is supported for Codex and, on macOS and Linux, for Claude
Code background tasks the node started. Claude status measures the process
behind the task's background session: the `pid` that `claude agents --json
--all` lists while the process is alive, and that process's start time. The node
re-reads both at every status, because the supervisor may stop and restart a
session's process, so a restart is a new run with a new run version. Only a
`working` or `blocked` session with a live process is `running` and stoppable. A
finished session whose process still runs, or a `working` or `blocked` one
without a live process, is `idle`; an ended one without a process is `closed`. A
row that lists no `pid`, or a missing row, is measured from the pid and start
time recorded on the task: `closed` needs that process ended (start time null or
changed), while it lives the session is `idle` (or `running` for a `working` or
`blocked` row; a missing row answers from the task state, `idle` for an ended
task and otherwise `unknown`), and an unreadable start time is `identity_unknown`. A
failed listing, an unreadable start time, or a row that is not the task's own
background session (by kind, short id, session id or name) is
`identity_unknown`. A Claude stop re-measures the run, captures the session
process and the descendants it has at that moment, each with its start time (by
parent, not by process group: a shell command runs in its own group), then runs
`claude stop <short id>`, the supported stop, so that the supervisor does not
restart the process, and waits for every captured identity to end. The listing
shows the session `stopped` without a `pid` while its process still lives, so
the row is never the evidence. The tree is captured again from every captured
process that still lives, once `claude stop` has returned and again before each
signal, so a process that a survivor started during the stop is waited for and
signalled too. A process that outlives the grace period, in practice a shell
command `claude stop` does not end, is signalled by its own pid, SIGTERM then
SIGKILL, only while it still has its captured start time. The session process
itself is never signalled: it was measured to end 1.7-1.8 s after `claude stop`
returns, and if it still lives after the grace period the stop ends
`stop_failed` with `processState` `running` without a signal, because the
supervisor's reaction to a signalled session is not measured and ending its
commands while it lives is no stop; the listing then shows the session `stopped`
without a `pid`, so a later status measures the recorded pid and start time
instead and answers `idle` while that process lives and `closed` once it ended
(issue #454); a `task stop` meanwhile is `stale_run`, and the operator ends a
lingering process locally. The stop is confirmed only when every captured
identity ended; a `claude stop` that fails, a survivor after SIGKILL, or a tree
that passes 256 processes is `stop_failed`, a session the supervisor restarted
in the meantime is `stale_run` with the new run recorded for the next status. A
process whose ancestors all ended before a capture, for example a background
job left by a command that finished during the grace period, is not reached;
this is the limit of the Codex stop as well (issues #231, #233). On Windows the
Claude stop stays refused (`unsupported_runtime`, `stopSupported: false`, issue
#460). Measured on Claude Code 2.1.289: the listed pid is the session process
and `claude stop` ends it within about 2 s, but the Bash tool runs a command
through Git Bash (MSYS), whose intermediate process exits, so the command's
parent is gone and it is not in the captured tree; the command and its shell
chain outlived `claude stop`, and a confirmed stop would confirm while the
command still runs. Lifting the refusal needs a capture that does not depend on
the parent chain, for example a job object or the MSYS process table.
The stop was measured on macOS; Linux runs the same code path and is not
measured separately.
A stop succeeds only after the target verifies that the captured process
tree ended. A changed run, uncertain identity, failed termination or recovery
state cannot produce `stopConfirmed: true`. Durable stop intent prevents an
automatic wake from starting the same task again; explicit continue clears it.

A timeout does not cancel a submitted operation. If the initial status times out,
the CLI says that no stop was submitted; resolve that status and rerun `task stop`.
If the stop itself is pending, retain its printed request id and use `task result`.
An interrupted execution is recovered as `recovery_required`, without automatically
repeating the process signal. A completed result is retried until acknowledged.

Authorization is at the enrolled-node boundary. The Worker derives ownership from
the original delegated request or authenticated source message; session labels are
not separate chat credentials. Operator-owned tasks, another node's tasks and
conflicting registrations are denied. Task owner, target and runtime stay immutable;
source-message discovery can move to a newer task without reassigning an older task.
Capabilities, revocation and local target policy are checked again during execution.
Only allowlisted metadata crosses the task-control protocol: no message text,
transcript, local path or process id. The exception is `reportedReason` above, the
target's own `task.report` reason of at most 256 characters. See [Architecture](ARCHITECTURE.md) for the
registration, operation and result flow.
### Intercom sessions

Issue #74. The first message of a conversation with another node goes either to an existing session there (`msg send <node>/<session>`) or to a new intercom session the Control Plane starts for it. The operator decides which, before the first message; the session never chooses on its own (the ROUTING rule under Peer coordination, for Claude and Codex).

- `msg send <node> --new claude|codex --directive "<the operator's answer>" [--cwd <dir>] -- <text>` resolves the node by id or name from the directory and writes a delegated task request (see [Delegated tasks](#delegated-tasks)) with `requirements.node` set to that node, the runtime and `--cwd` as requirements, the label `intercom: <own runtime>@<own node name>` as `label` and `title`, and the text as the task text. The sender passes the check of `msg send` first. The own runtime is `codex` for a `--from` that names a recorded Codex session, otherwise the runtime that runs the command, decided as for the sender (issue #471). `--directive` is required and quotes the operator's answer to the question existing session or new intercom session verbatim; it becomes the task's directive. There is no default, because a default would claim an operator choice nobody made: without `--directive` the CLI exits 1 with `--new needs --directive with the operator's answer` and writes nothing. It also exits 1 and writes nothing (issue #240) for a `--cwd` that cannot be a directory on the target: a path that Git Bash path conversion rewrote into the Git for Windows install directory (for example `C:/Program Files/Git/Users/...` from `/Users/...`), on any target, and, when the target's path style is known from the working directories of its sessions in the directory, a Windows drive path for a node with POSIX paths or a POSIX path for a node with Windows paths. The error names the problem and the fix: run the command from PowerShell, or set `MSYS_NO_PATHCONV=1` in Git Bash. A target that lists no session gets only the Git Bash check; its own admission still refuses an unusable directory.
- It then waits (default 30 seconds, `--wait`) for the Worker's answer that the daemon records, prints the task id, then (issue #198) a notice that it is a background task on that node, a Control Plane task and not a desktop app chat that the Codex and Claude desktop apps may not list, with the commands for its status (`kherep-node task status <taskId>`) and transcript (`msg sessions` marks it `[background task]`; `kherep-node attach <node>/<its session id>` prints the command that opens it), and exits 0; a refusal prints `refused: <reason>` and exits 1, as does no answer within the wait (the request stays pending; `task show <requestId>` shows it later). The checks of `task new` apply first and fail at once: no chains, `sessions.delegate.request` on this node, no active task on this node. The target needs `sessions.delegate.accept`, sessions enabled and its limits; the Worker refuses with the reason when it does not qualify.
- The target starts the session as a background task named `task-<8>` with the label recorded; `msg sessions` shows it under its label. The framed prompt adds that it is an intercom session for a conversation with `<nodeId>/<session>` and the answer as one ready command, `<cli> msg send <nodeId>/<session> -- "<answer>"` with the `<cli>` of the framed prompt (see [Tasks](#tasks)), plus that for a plain question this reply is the only required action before the session reports done (issue #79). Later messages of the conversation are ordinary `msg send` messages to that session.
- Needs a Worker that knows `requirements.node` and `label`; an older Worker refuses such a request as an invalid body, and an older node refuses a `session.start` with a `label`.

#### Messages for a closed session

Issues #102 and #105, operator decisions of 2026-09-27: a message must reach its target without any user action, even when the target session was closed, and at the lowest cost in context. With `"resumeClosed": true` in the `messaging` section of `policy.json` (only the boolean `true` enables it; any other value leaves it off), the daemon, after each session listing, looks for `accepted` messages whose target a listing taken after their arrival did not show, that is closed by the rule below, and that names a session this node knows: a session in `known-sessions.json` (every successful listing is merged into it and kept 7 days), a Codex session in `codex-sessions/`, or a task record. An unknown target is left to the refusal after 60 minutes as before. Such a message is sent by the full session id, since a closed session is no longer in the directory (`msg send <node>/<full session id>`, issue #107); the node accepts it only under an accept rule for that id or `*`, because the session's name is no longer in `sessions.json`. Such a message goes to an intercom session of its sender, never to the closed session itself: resuming that would reload its whole conversation (issue #105).

**Closure requires positive metadata** (#706 Phase 1). Consecutive listing misses remain diagnostic and cannot prove closed, archived or deleted. Complete fresh app absence also needs exact holder absence. Unknown or conflicting evidence keeps messages waiting, including after one hour. Authoritative archive/delete tombstones exclude the exact ID from publication and prevent legacy fallback; a newer authoritative restore generation is required to supersede them. The existing `resumeClosed` policy alone cannot bypass this deny-only gate. Fresh complete positive closure still needs every original three-miss/minimum-age, address, listing, policy, permission, depth and budget veto to pass before the existing fallback can proceed.

- **Reuse.** The node looks for the newest intercom session it started itself for the same sender: a task record with `local` `intercom` whose `requestedBy` is exactly the sender's `<node id>/<session>`, and that did not fail to start. Each sender session therefore has its own intercom session on this node; another session, even on the same sender node, gets its own. When that intercom session is still running, the message is handed to it: its inbox record is readdressed to the intercom session (`toSession`, with the closed session kept in `closedTo`), and its delivery hook or its wake listener offers it as for any message. The wake takes it through the task grant, which for such an intercom session covers the messages of the session it answers, since those carry no task id. When the intercom session has ended and its session id and a delegated mode (`auto` or `default`, allowed by `sessions.permissionModes`) are recorded, the messages are readdressed the same way and the session is resumed in the background in its recorded mode and working directory. Claude Code: `claude --resume <session id> --bg --permission-mode <mode> "<wake text>"` ([agent view, from your shell](https://code.claude.com/docs/en/agent-view): "To continue an existing conversation in the background, pass its full session ID with `--resume`"; [permission mode on resume](https://code.claude.com/docs/en/sessions): "Pass `--permission-mode` ... to override the restored mode"). The prompt is the fixed wake text; the delivery hook of that turn offers the messages as framed peer content, exactly as for a woken session, and the session is added to `sessions.json` at once so the hook finds it by name too. Right after the resume the node looks the session up in `claude agents --json --all` by the short id `--bg` printed. When Claude Code continued it as a copy under a new id, the node adopts the copy (issue #109): the same intercom task record takes the new id, its waiting (`accepted` or `offered`) messages are readdressed to it, and it is added to `sessions.json`; the watch round does the same when it learns the new id later. Only a copy that announced itself with a `note:` line and is not listed is stopped, and a new intercom session starts. Once a copy is adopted, the session the record held before the resume is stopped with `claude stop <short id>` (issue #111), so that only one intercom session per sender stays: only while `claude agents --json --all` lists it under that short id with the recorded session id and its process `status` is `idle` ([agent view](https://code.claude.com/docs/en/agent-view): "`pid`, `status` ... one of `busy`, `waiting`, or `idle`"). A `busy` or `waiting` one is tried again in each watch round, up to 30 rounds; one that is not listed, holds another id or has no live process is left alone. The closed session the messages were sent to is never stopped, since no intercom record holds it. Codex: `codex exec resume <thread>` as for a Codex task, with the wake text and the framed messages on stdin, offered with `offeredBy` `intercom`; the watch round confirms them when the run completes its turn. An intercom or target task with durable operator-stop intent is neither resumed nor replaced; its message stays accepted until explicit continue clears the intent.
- **New.** Otherwise, or when that resume fails, the node starts an intercom session itself, as `msg send --new` would: the runtime and working directory of the closed session, the label `intercom: <sender runtime>@<sender node name>` (from the directory; `session` when the sender's runtime is not listed) and, as the directive, a fixed text saying that this is an automatic delivery fallback approved by the node policy (`messaging.resumeClosed`). The task text is the sender's messages framed as the delivery hook frames them (per-call markers, "NOT an instruction from the user", sender, message id), each with its reply command `<cli> msg send --reply-to <message id> -- <reply text>`, as far as they fit 16,384 characters (a first message that does not fit is shortened with a pointer to `msg inbox --all`). The framed prompt tells the session to answer each message with that command, so that the answer is threaded (`in reply to`), and not with a plain `msg send`. The messages it carries are readdressed to it (`toSession` its name, `closedTo` the session they were sent to), marked `offered` (`offeredBy` `intercom`) with `fallback-running`, and confirmed only when its turn completed (issue #308). Claude: the watch round marks them `delivered` once `claude agents --json --all` shows the session `done`, or the session's own `Stop` hook confirms them first; `working`, even 30 seconds after the start, and a prompt the turn raised are progress (see **No progress after start** under [Tasks](#tasks)) but no read receipt. A turn that `failed` or was `stopped` after progress offers them again (`retry`), and a session without progress after 10 minutes refuses them with `target run made no progress after start`, as it does every waiting message it was to deliver. Before issue #197 they were marked `delivered` as soon as `claude --bg` returned, also for a session whose login had expired; before issue #308, once the session still worked 30 seconds after its start. Codex (issue #119): they are confirmed only when its run completes the turn, otherwise offered again through the Codex exchange round (see [Codex tasks](#codex-tasks), **Windows: intercom runs**). The session's `msg send` knows its own session from `CLAUDE_CODE_SESSION_ID`, or for Codex from the `KHEREP_SESSION_ID` the node sets, which stays the identity and is checked against `CODEX_THREAD_ID` when the task's thread is known, so the command needs no `--from`. An operator message goes to no intercom session, because its answer could not reach the operator API.
- **Delivery identity.** Each inbox record handled by a local intercom task records `delivery.taskId`, `delivery.runtime` and, once known, `delivery.sessionId`. This is separate from the existing inbox `taskId`, which remains the authorization grant. Offers, retries and receipts preserve the delivery identity. A failed start or resume leaves an accepted message without a delivery association. New, running and resumed Claude and Codex intercom paths update it; a Claude copy updates the same messages to the adopted session. When a start has no session id yet, the task record keeps only those message ids until its watch maps the session; resolving that list does not scan unrelated records.
- **Copy handover recovery.** Both immediate Claude resume-copy adoption and a later watch use the same two-phase operation (issue #635). Every waiting (`accepted` or `offered`) message at the previous address moves as before, including messages with another delivery owner, whose identity stays unchanged. The handover also recovers pending intermediate messages with the exact delivery task and runtime, even when `closedTo` retains an older original address. It then corrects only that task/runtime's delivery session metadata at the actual destination, including messages already consumed there; terminal messages at other addresses stay unchanged. Record locks recheck current ownership/address/state and preserve original provenance, attempts and offer/retry evidence. A busy watch leaves the mapping for retry; a busy immediate resume restores the old mapping with the new short ID so the watcher can finish without a second launch. This scan occurs on adoption only: historical orphans without another adoption are not swept. Unowned intermediate messages still require the existing opt-in fallback path, including `messaging.resumeClosed` set to `true`, accepted and unattempted state, a known resolvable closed target and all policy/readiness/budget guards. A crash after immediate resume's early task save is not covered by the retry guarantee.
- **Malformed session ID** (issue #638). A listed full session ID that is not a valid session reference (over 128 characters or with a control character) is never adopted. The watch round leaves only that task as it is, including its no-progress clock, carried messages and copies, while later tasks go on; its max runtime is still enforced through the short ID. An immediate resume listed under such an ID keeps the resumed session with the old full ID until a valid listing maps it, and starts no second session; its messages stay at the old ID and can be refused after 60 minutes under the existing rules (see **Guards**). An error after a resumed session was kept, such as a failed write, no longer starts a second session either. A resume that printed no session ID, or a `note:` copy that is not listed, still falls back to a new intercom session. An empty listed ID keeps its previous behavior. A start or continue listed under such an ID (issue #639) maps it as missing: a new start, the intercom session of **New** included, keeps its short ID, process and pending marker without a full ID, and its messages stay delivery-pending under the task name until the watch round maps a valid listing; they stay offered until its completed turn delivers them. A continue keeps its previous valid full ID while pending. The attempt is still marked before the start. An ended intercom session whose recorded full ID is not a valid session reference is not resumed, since that ID would key its turn budget: its messages take **New** with the closed session's runtime, working directory, limits (its old task counts toward `maxStartsPerDay`) and budget. The direct resume keeps its own refusal of such an ID. Existing records are not migrated, and an active or still-running intercom session is handled as before.
- **Guards**, fail closed, each refusal audited with its reason: the wake kill switch; the [readiness](#tasks) of the runtime that would run (not signed in: the messages are refused with `target runtime <runtime> not ready (sign-in required)` and get no attempt; without a verdict, or after a probe that timed out or failed, they wait with `retry-pending` and no attempt); `sessions.enabled` with the runtime in `runtimes`; `sessions.delegate.accept` and an accept rule for the sender; reply depth below 6; never a closed session whose recorded mode is `bypassPermissions`; `maxConcurrent` (and, for a new session, `maxStartsPerDay`); a working directory inside the workspace roots; and one autonomous turn of the budget of the session that runs, the resumed intercom session or, for a new one, the closed session (by default 20 per hour, 100 per day, 30 seconds apart; `wake.budget`). A new session also passes the checks of every task start. A refused admission waits until positive terminal metadata permits refusal. A message handed to an intercom session (`closedTo` set) is judged by its current `toSession`, and a message a session answered with `msg send --reply-to` is `delivered`, even when no turn offered it (issue #111).
- **No loops.** A message causes at most one attempt (`closedAttempt` in its inbox record), a closed session gets one run per round, and none while a run for it is active. These sessions do not use the regular Worker task reporting path: their task records carry `local` `intercom` (`resume` in records written before issue #105), send no `task.report`, and their messages carry no task id. When owner task control is enabled, a separate metadata-only registration associates their local task with the authenticated source message. While such a session is active it counts against `maxConcurrent`, and the node sends no task requests, as for any active task.
- Every outcome is a line in `wake.jsonl` with the action `closed-session` and the outcome `reused` (reason `intercom session running` or `intercom session resumed`, with the intercom session's `taskId`), `new` or `refused`, plus the reason; a stopped previous copy has the outcome `retired-copy` and one kept after 30 busy rounds `copy-kept`, each with its `sessionId`, `shortId` and `taskId`; message text is never written.

The progress code a sender reads for a refused message (issue #230) names the guard that refused it; only a start or resume that failed is a failure. A refusal before the attempt leaves the message for the next round. All codes but `cwd-refused` exist since issue #197, so `isNodeMessageStatusBody` on an older Worker accepts them; `cwd-refused` (issue #396) needs an upgraded Worker ([upgrade order](#session-messaging)), which hands it to a sender without `messaging.progress.v2` as `wake-not-authorized`.

## Security model

- **Node identity.** `kherep-node node onboard` generates an Ed25519 key pair locally. The private key is written as PKCS#8 PEM to `node-ed25519.pem` in the node's config directory with mode `0600` on POSIX systems; on Windows it inherits the ACL of the per-user config directory. It never leaves the host.
- **Enrollment.** An operator creates a one-time code through the API (default 10 minutes, bounded to 1-60 minutes, single use; only its SHA-256 hash is stored). The node sends the code, its public key, name, host facts and discovered runtimes to `/node/enroll`, and the registry binds a new `nodeId` to that public key.
- **Connection.** `/node/connect` is gated only by the signed challenge; nodes hold no Cloudflare Access credential. The server sends a random nonce; the node signs `kherep-control/v1/auth`, the nonce, its `nodeId` and a timestamp. The connection is accepted only for an enrolled, non-revoked key, a nonce issued on this connection within 30 seconds, and a timestamp within 60 seconds of server time. A captured auth message cannot be replayed on another connection because every connection gets a new nonce.
- **Operator API.** Every `/api/*` request must carry a valid `Cf-Access-Jwt-Assertion`. The Worker verifies it with `jose` against `<team domain>/cdn-cgi/access/certs`, with the team domain as issuer and the Access application AUD as audience, even behind an Access application, so a misconfigured route cannot expose the API. Without both values configured, `/api/*` answers 503.
- **Revocation.** `DELETE /api/nodes/{id}` deletes the key binding, marks the node revoked, clears its pending commands and closes its socket. Rotation is re-enrollment with a new key. `kherep-node node unenroll` destroys the local key and config and prints the `nodeId` for the operator to revoke; Phase 1 has no node-initiated revocation call.
- **Audit.** Enrollment, status changes, command dispatch and revocation are written to the registry's `audit` table with the acting identity. Every message send (from a node or through the API) and every message state change is audited with the message id, the target session, the state and the reason; message text never enters the audit table.
- **Session messaging.** A message reaches a session only through the node policy, and then only as framed peer content that tells the model it is not an instruction from the user. The session tools never talk to the network; they share files with the daemon in the per-user config directory. The Worker verifies the sender node of a message; the sender session is whatever the sending node reports.
- **Tasks.** Only the operator API and a delegated request that passed the checks of both nodes and the Worker queue a session command; a node runs it only with sessions enabled in its own policy, inside its workspace roots, within its limits, never in `bypassPermissions`, and Codex tasks only when its policy lists `codex`, in a Codex sandbox, never with a bypass flag. The task text stays out of the audit table; see [Tasks](#tasks).
- **Message text retention.** The Worker keeps a message's text only while the message is `queued`. When the target node accepts it, or it is refused or expires, the text column is set to `NULL`; a message refused on send is stored without text. The remaining metadata (ids, sessions, state, reason, timestamps) stays in the `messages` table. The API never returns message text.

Then put a Cloudflare Access application with an allow policy for the operators in front of `control.example.com/api/*`. Leave `/node/*` outside Access. Deploying and creating these resources is an operator action; the repository never does it.

Durable Object classes are declared with the `exports` map, which replaces the legacy `migrations` array. A Worker deployed earlier with `migrations` (tag `v1`, `new_sqlite_classes`) moves to `exports` without data migration; the move is one-way, so do not return to `migrations` afterwards.

#### Observability and SQLite cost

The committed `wrangler.jsonc` and the override example above turn on Workers Logs for every invocation (`"observability": { "enabled": true, "head_sampling_rate": 1 }`). It takes effect only when the operator deploys with an override that carries it; the repository deploys nothing. Each Registry request then writes one log line, for example:

```json
{ "event": "registry.sql", "path": "sendMessage", "rowsRead": 6, "rowsWritten": 9 }
```

`path` is the Registry method; `rowsRead` and `rowsWritten` are the SQLite rows that the request's cursors read and wrote (`worker/src/sql-meter.mts`). The line carries no message text, session or identity, and no duration: time does not advance in synchronous Durable Object code. Every request path runs its SQL in one synchronous region, so no row is counted for two requests. SQL outside a request, such as the schema set-up when the Registry starts, counts only toward the totals of `Registry.sqlStats()`. Each line is a log event and counts toward the Workers Logs limits of the account's plan.

Durable Object SQLite storage is billed by rows read and rows written. The Workers Free plan includes 5 million rows read per day ([Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/)). Costs per request measured by the Worker tests with 2,000 final-state messages and 500 sessions (issue #308):

| Request path | Rows read before | Rows read now | Rows written now |
| --- | --- | --- | --- |
| `sendMessage` (`message.send`) | 4,009 | 6 | 9 |
| `sendMessage` (a reply to a deleted message) | - | 9 | 10 |
| `reportMessageStatus` (`message.status` from the target) | 2,008 | 9, a final state 10 | 7, a final state 8 |
| `ackMessageStatus` (`message.status.ack`, deletes the row) | - | 6 | 6 |
| `ackMessageStatus` (settles a row stored before PR 4, issue #493) | - | 6 | 3 |
| `messageStatusPageFor` (reconnect replay, a sender with 3 unacknowledged and 2,000 acknowledged messages) | 2,004 | 4 | 0 |
| `directory` (`directory.get`) | 504 | 0, or 504 after a write to nodes, runtimes or sessions | 0 |
| `alarm` (nothing due) | - | 6 | 0 |
| `alarm` (a full batch: 64 deletions and 64 pruned tombstones) | - | 324 | 448 |

`messageSummary` (`GET /api/messages/summary`, issue #493) is a diagnostic, not a hot path: it reads every row of the requested sender through `messages_from_node`, two rows read per stored message of that sender (the index entry and the row; the tests measured 600 for 300 messages) plus at most one index entry past the range, and no other sender's rows. It writes nothing. Like every `/api/*` route it requires a valid `Cf-Access-Jwt-Assertion` and reads no other header as the Access token.

PR 4 (deletion after acknowledgement) measured these with 4,000 further final rows that carry a fallback deadline and 4,000 tombstones in the tables. Each message request also reads the earliest deadline and the oldest tombstone to arm the alarm; that is one row each, whatever the table sizes. Its queries name `messages_delete_after` (a partial index of rows with a fallback deadline), `tombstones_deleted_at`, the primary keys of both tables, and `messages_from_node` for a revocation.

Before, a send scanned the `messages` table twice and a status report or a replay page once, and the table keeps every final-state row, so the cost grew with every message ever sent; doubling the messages doubled these reads. Now the hot queries name their index (`INDEXED BY`): `messages_queued_expiry` (queued rows by expiry) and `messages_replay` (replay; partial over the rows whose current state differs from the acknowledged one, `settled_state IS NOT state`, issue #493, where `messages_from_node` served the replay before). A third index, `messages_state_updated` (state and last change), is created now for a later sweep of final-state rows and is not read yet. Doubling the messages leaves the "now" column unchanged. Each index adds a written row when a write touches its columns: a send now writes 9 rows instead of 5, a status report 7 instead of 4 (with `messages_replay`, issue #493, which a write that sets `state` also touches). The indexes are created on the first Registry start after the deploy, which reads the `messages` table once.

### Node

Node.js 22.18 or later on the 22 line, or 23.6 or later, no dependencies:

```sh
# The operator creates a code: POST /api/enrollments (through Access)
KHEREP_ENROLL_CODE=<code> node modules/control-plane/node/cli.mts node onboard --url https://control.example.com --name build-01
node modules/control-plane/node/cli.mts node status
node modules/control-plane/node/cli.mts daemon
node modules/control-plane/node/cli.mts doctor
```

After enrollment, `kherep-node service install|upgrade|status|rollback` manages
the daemon as a per-user macOS LaunchAgent or Windows Scheduled Task. The
service runs the product runner from a verified source pin, records that source
once at daemon startup and retains exported Windows task definitions or configured
macOS plist bytes with their security metadata. Existing definitions require
explicit adoption by exact name. macOS adoption makes the on-disk plist
authoritative and refuses observable loaded-origin, action or log-path mismatch;
a complete previous launchd memory-cache snapshot remains unknown. The
Windows task runs a fixed product Node supervisor that verifies the pin before
each child start, appends both daemon streams to the retained service log and
restarts an exited child after 30 seconds. A generation-bound one-use permit lets
only the transaction's candidate start while admissions are drained. A stop
is refused when ownership, source, service binding or descendant absence is not
proven; on Windows it retains the attested supervisor and daemon handles, stops
the supervisor first and never reopens a pid after that boundary. Read-only
Windows probes may wait for positively owned daemon descendants to exit, with
fresh identity, definition and security checks on every probe. The polling budget
is 30 seconds. The mutating stop repeats the complete read-only check inside
its same native invocation before its first effect, then runs one stop sequence
under a 65-second bounded call that includes both retained-handle exit waits.
It never follows a replacement pid or retries a mutation. The
transaction drains new task admissions, waits for an admission that already
holds a lease, and rechecks ownership immediately before the selected service
stop. Admission leases carry PID, start-time and owner provenance;
positively stale leases are recovered and uncertain owners fail closed. Status
succeeds only for a running, authenticated daemon with the exact managed
process, source, config and service binding. A failed activation never leaves
a definition on disk that differs from the loaded job: a candidate that recovery
cannot stop stays loaded and is recorded in `service/candidate.json`, and the
next upgrade, rollback or repeated install stops it through the proven path
(issue #582). It does not modify Claude Code or Codex hooks.

`service install`, `upgrade` and `rollback` also write the stable command to
`bin/` under the config directory (issue #436): `kherep-node.mjs`, a POSIX shim
`kherep-node` and, on Windows, `kherep-node.cmd` and `kherep-node.ps1`. Agents
and scripts run

```sh
node "<config directory>/bin/kherep-node.mjs" msg sessions
```

with forward slashes on Windows (`node "C:/Users/<user>/AppData/Roaming/kherep/bin/kherep-node.mjs"`)
and the path in double quotes, since the macOS default contains a space. The
command needs no PATH entry, no `.cmd` resolution and no PowerShell call
operator; nothing changes PATH, and the shims are for operators who add `bin/`
themselves. At every call the launcher reads `control-plane/service/receipt.json`
of the config directory (derived as below) and runs the receipt's Node
executable with the active pin's `modules/control-plane/node/cli.mts`, passing
the arguments, stdio and exit code through. Its files never name a pin, so
upgrade and rollback change only the receipt and the launcher keeps its bytes;
it imports nothing from a pin and leaves digest verification to the service
transaction. A missing or unreadable receipt, one that names no verified pin, a
missing pin or a pin without the CLI exits 1 with
`kherep-node: <reason>; receipt <path>; run "kherep-node service install|upgrade" from a clean checkout`,
with no fallback to a checkout or to `node` on PATH. A rollback to a legacy
service without a prior receipt keeps the launcher, which then fails closed.
The files are rewritten only when their bytes differ, and the JSON result of the
three commands reports `launcher` as `written`, `unchanged` or `failed`; a
failed write does not undo the activation.

The command works from Git Bash with and without path conversion, but Git Bash
still rewrites a `/`-leading argument such as `--cwd /Users/...` before Node
sees it: set `MSYS_NO_PATHCONV=1` or use PowerShell for those. PowerShell drops
a literal `--` before the `.ps1` shim sees it, so message text that starts with
`-` needs the canonical command or `kherep-node.cmd`.

Readiness probes, session discovery and native Codex Queue reconciliation take
the same admission when their lane actually executes. Work queued before a
drain waits and resumes without consuming attempt or budget records or
publishing an empty result. Nested Queue work reuses its opaque admission, and
the lease remains until each helper has exited and closed its streams. An
unconfirmed helper shutdown leaves a fail-closed lease for stale-owner recovery.

The Worker keeps one authenticated connection per node identity. A daemon whose
connection is replaced by a newer connection for that identity exits on close
code 4409 instead of reconnecting. Close code 4403 is also terminal; transient
transport closes retain the bounded reconnect backoff. If the replacement was
unintended, stop the newer daemon before restarting the intended one.

`ready` in the runtimes check is the running daemon's last [readiness probe](#tasks) of that runtime, read from `daemon.json` (issue #222); doctor never probes. It is `true`, or `false` with `cause` (`sign-in`, `timeout` or `error`), each with `probedAt` and `aged`, or `"unknown"` when the daemon is not running, has not probed that runtime (it probes only the runtimes the sessions policy enables) or the record is malformed. `aged` is true once the probe is older than the daemon's own revalidation bound (10 minutes ready, 2 minutes not ready). An aged verdict is still reported: the daemon keeps advertising and acting on it until its next probe, and it probes a ready runtime again only when a run needs it, so an idle node shows an aged `true`. Only `sign-in` fails the check, because only a sign-in failure makes the node refuse a task; a timed-out or failed probe blocks nothing. `runtimes.claude.lastStopInterruptedProbeAt` names the start of a Claude probe that the last daemon stop interrupted, while `daemon.json` records it; it never fails the check (issue #420). The daemon check needs a daemon of this version, since older daemons do not write `daemon.json`.

The `intercom` check (issue #436) covers the stable command `node "<configRoot>/bin/kherep-node.mjs"`. Without a receipt it reports `managed: false` and fails, since the command cannot resolve a pin; an invalid receipt fails with `managed: true`, and in both cases only `receipt` and `instructions` are reported. The pin's full digest is checked here, once per doctor run; the launcher itself checks only that the pin's manifest and CLI exist. The five instruction files are `claudeUser` (`CLAUDE.md` of the Claude config directory), `claudeRouting` (`teams/kherep/ROUTING.md` there), `codexAgents` (`AGENTS.md` of the Codex home), `codexRouting` (`orchestra/ROUTING.md` there) and `codexRules` (`rules/kherep-control-plane.rules` there). A file is `present` when it holds the exact command, the rules file when it is exactly the file `codex/install.mts` writes, the launcher's `prefix_rule` alone; the expected text comes from the installers' own renderers (`bootstrap/render-intercom.mts`, `codex/lib/control-plane-rules.mts`); `stale` means it exists without it, as a file still naming only a pin's `cli.mts` or an unrendered `__KHEREP_NODE__` does. A failed read is `unreadable`, never `missing`. The check reports paths and these fixed statuses, never file contents, the receipt's digest or any message.

The `queueDrain` check (issue #441) reads `directory.json` and `node.json` only; it never asks for a refresh or fetches. A queue it did not measure is `ok: false, measured: false` with a fixed `detail`, never zero: no or an invalid `directory.json`, one older than 3 minutes or dated ahead of this clock, no `intake` for this node (an older Worker), or this node not listed (in a complete or a truncated directory). On a truncated directory `peers` describes the listed peers only and `detail` says so. `intakeLatency` (issue #441, part A) sees only messages that reached this node's inbox; `queueDrain` sees those still queued at the control plane, and the daemon's `lane` log lines say why a queue stalls: `lane <lane> item <kind> took <s> s` for an item that ran over 5 seconds (ending `, waited <s> s` when it also waited that long), `lane <lane> item <kind> waited <s> s, took <s> s` for one that waited over 5 seconds behind earlier items of its lane (issue #487), and `round sent <n> status/<m> outbox frames, handled <k> inbound items` after an exchange round that sent, or a period between two rounds that handled, more than 32 frames. When it handled any, the line goes on with `: <kind> <n>, ...` (issue #493): the eight most frequent kinds by count (ties in a fixed order), then `other <n>` for the rest. Kinds come from a closed list of 43 labels, never from a received string: `pong`; `auth`; `frame:event:receipt`; `task-control:status|stop`; `frame:event` for any other event; `command:<name>` for the six node commands, `command:unknown` for any other command name and `command:invalid` for a malformed command; `frame:message.status:<state>` for the six message states and `frame:message.status:invalid`; `frame:<type>` for each other protocol message type; `frame:invalid` for a frame that does not parse (oversize, not JSON, an unknown type); and `unknown` as a defensive bucket. Each frame is counted once, on the lane that finally handles it; the count resets after every round, also one that logs nothing. After a connection ends, `disconnected (<code>, clean=<true|false>, error:<class>); reconnecting in <s> s` gives the close code, whether the close was clean, and the class of the last socket error on that connection: one of `ECONNRESET`, `ETIMEDOUT`, `ECONNREFUSED`, `ENOTFOUND`, `EAI_AGAIN`, `EPIPE`, `EHOSTUNREACH`, `ENETUNREACH`, `ENETDOWN`, `UND_ERR_SOCKET`, `UND_ERR_CONNECT_TIMEOUT` when the error's `code` is that string, `unknown` for another code, `missing` when the error carries no string code, and `none` without an error event. No error message, close reason or URL is logged. All of them carry kinds, closed codes and counts only.

The `wakeReadiness` check uses only a successful local session snapshot no older than two daemon scan intervals. The snapshot writer preserves which runtimes the listing could not see. Doctor labels a fresh snapshot `complete`, `partial`, or `unknown` for a legacy file; every count describes only observed rows, so a zero from a partial or legacy snapshot is not a total-population claim. A missing, unreadable, malformed, future-dated or stale snapshot makes observed idle state `"unknown"`. It reports observed policy eligibility separately from exact `SessionStart` authorization, remembered permission evidence and live listed-listener evidence. A verified listener entry requires matching lock and scope tokens, `listed: true`, a live process and an age within the listener deadline. It does not prove that the listener is currently idle, that the kill switch permits waking, or that a message was received, so the check derives no ready verdict. A missing lock is distinct from a failed lock read. Missing explicit restart authorization is reported as a prerequisite, not asserted as the cause of every absent listener. The check reports only aggregate counts and fixed details: no key material, listener tokens, session ids, paths, response bodies or message text.

### Node messaging

Messaging is off unless `policy.json` accepts it. `kherep-node node onboard` writes a new `policy.json` with the explicit rule `"messaging": { "accept": [{ "session": "*", "from": ["*"] }] }`, which accepts every sender of this control plane (authenticated nodes and the operator API) for every session, and a missing file reads as that default policy (issue #390). An existing file without a `messaging` section is never given that rule implicitly: it accepts nothing until the operator writes one. The `messaging` section lists which senders may leave a message for which local session:

```json
{
  "version": 1,
  "allowedCommands": ["node.status", "runtime.list", "session.list"],
  "messaging": {
    "accept": [
      { "session": "review", "from": ["operator", "00000000-0000-4000-8000-000000000001"] },
      { "session": "*", "from": ["00000000-0000-4000-8000-000000000002"] }
    ]
  }
}
```

- `session` is the exact session id or name a sender addresses, or `*` for any session on this node. `from` lists sender node ids, `operator` for messages sent through the API, or `*` for any sender.
- A missing section or an empty `accept` list disables messaging; waking, on by default, then has no message to act on. A malformed section disables it as a whole, fail closed; the command allowlist is unaffected.
- `"resumeClosed": true` next to `accept` lets a message for a session of this node that is no longer running go to an intercom session of its sender, an existing one or a new one ([messages for a closed session](#messages-for-a-closed-session)). Off unless it is the boolean `true`.
- The daemon reads the policy at start and again at every exchange round, session check and command; every section (`allowedCommands`, `messaging` including `resumeClosed`, `wake`, `sessions`, `remoteMcp`) takes effect without a restart. It advertises `messaging.v1` in `register` only when at least one accept rule exists, and `messaging.ack.v1` (issue #308) and `messaging.progress.v2` (issue #396) always.
- The optional `wake` section decides which sessions the wake listener may wake; a running listener reads it again at every poll ([listening while idle](#listening-while-idle)).
- An accepted message is written to `inbox/<messageId>.json` atomically (a temporary file renamed into place) with `messageId`, `from`, `toSession`, `text`, optional `inReplyTo`, `createdAt`, `receivedAt` and `state` `accepted`. A redelivered message keeps the existing file. When the file cannot be written the node sends no status, so the Worker keeps the message queued and delivers it again after the next authentication.
- The delivery hook, an MCP `inbox` read and the daemon move a record on to `offered`, `delivered` or `refused` (see [Delivery hook](#delivery-hook) and [Session messaging](#session-messaging)). `offered` is local only.
- Records older than 7 days are removed by each daemon start, after its first authenticated connection (or 60 s after its start without one) and in the background (issue #581), after it recorded `replied` for each sent message a reply in the inbox answers (issue #520), but never silently while the sender could still see them accepted (issue #195): a record still `accepted` or `offered` is refused with reason `not delivered within the inbox retention period` and reported like any refusal, and a final record stays until its receipt confirms that state, or for one more retention period without one. A record written while that pass runs, or within the two seconds before it began, for example one refused meanwhile, waits for the next start.

Runtime discovery checks `PATH` for `claude` and `codex` without running them, then the per-user and package-manager directories that a service's minimal `PATH` (a macOS LaunchAgent, for example) lacks: `~/.local/bin`, `~/.claude/local`, `~/.npm-global/bin`, `/opt/homebrew/bin` and `/usr/local/bin`, or `%APPDATA%\npm` on Windows. Session discovery uses the same lookup; a Windows npm shim (`claude.cmd`) is replaced by the native `claude.exe` shipped next to it, a shim without one runs through `cmd.exe` with a fixed command line, any other executable runs without a shell. Runtime discovery also probes LM Studio (`127.0.0.1:1234`) and Ollama (`127.0.0.1:11434`) on loopback only.

The control URL must be an `https` origin; plain `http` is accepted only for a loopback development Worker.

### Attach

`kherep-node attach <node>/<session>` (issue #81, operator decision of 2026-09-27, scope A) prints the command that opens a session on the host where it runs. It never runs the command and never opens a connection. No session content travels through the Worker: the command only reads the local directory, and the session is opened by the printed command over whatever path the operator uses to reach that host.

- The target resolves through the directory exactly as for `msg send`: the node by id or name, the session by full id, a unique name or label, or `codex-<8>`. A Codex thread title is never an address. An unknown or ambiguous target fails with the same message as `msg send`.
- Claude Code: `claude attach <short id>` takes the session over, `claude logs <short id>` follows it read-only. The short id is the first 8 characters of the session id, as `claude agents --json` shows it for a background session. A session the directory reports with `kind` `interactive` gets no command, only a note that it can be opened only where it runs. A session with `kind` `background`, or with a label (a task session the node started with `--bg`), gets both commands. For any other session both commands are printed with a one-line caveat that attach works only for a background session.
- Codex: the thread title, when the directory has one, and `codex resume <full thread id>`.
- Output is plain text: a header line and notes start with `#`, every other line is one command. An id that is not safe to print as a command argument is refused, and a runtime without an attach command fails.

The SSH prefix comes from the optional file `attach.json` in the node's `control-plane` directory. The operator writes it; the node never does.

```json
{ "ssh": { "mac": "me@mac.example.test", "00000000-0000-4000-8000-0000000000cc": "build-host" } }
```

- A key is a node name or node id; the id wins when both map the node. A value is an SSH host alias, host name or `user@host` of 1 to 64 characters from letters, digits, `.`, `_`, `@` and `-`, not starting with `-`.
- When the file maps the target node, each command is printed as `ssh -t <target> <command>`. A session on this node never gets a prefix.
- A missing file means no prefix. A file that is not exactly this shape, including an unknown top-level key or an invalid target, is an error that names the file, and nothing is printed.

Example with the mapping above:

```text
# mac (00000000-0000-4000-8000-0000000000cc) / intercom: claude@win (0f0e0d0c-1111-4222-8333-444455556666), claude-code, background session
ssh -t me@mac.example.test claude attach 0f0e0d0c
ssh -t me@mac.example.test claude logs 0f0e0d0c
```

Interactive `claude attach` over `ssh -t` is unverified.

### Attribution

`kherep-node attribution [--branch <name>] [--pr <number>] [--repo <owner/name>] [--since <hours>] [--json]` (issue #325) prints which session on this host pushed a branch or opened a PR, oldest first, one line per record, or the records as a JSON array with `--json`. Filters combine; `--branch` matches the local branch or the pushed remote branch, so `git push origin main:feat/x` is found under `feat/x`; `--since` counts hours back from now. It reads `attribution.jsonl` only; nothing is sent to the Worker or another node.

- **Pushes** come from the git `pre-push` hook beside `commit-msg`, for repositories under the workspace only (`KHEREP_WORKSPACE`, else the `workspace` line of `commit-policy`). It records one line per pushed ref and never blocks a push. The session is `CLAUDE_CODE_SESSION_ID` (Claude Code), else `KHEREP_SESSION_ID` (a Codex task the node started), else a marker the Codex `PreToolUse` phase of `attribution-hook.mts` left for that toplevel within 120 seconds, else `unknown` with `sessionSource` `none`. The remote URL yields only owner/name; userinfo never reaches the log.
- **`gh pr create`** never reaches a git hook, so `attribution-hook.mts` writes that record at `PostToolUse`, through the stable entry point like the delivery hook (issue #503 for Codex, #592 for Claude): in Claude Code for the Bash and PowerShell tools, in Codex with `--runtime codex` for its shell tools. The PR number comes from a `/pull/<n>` URL in the tool output, else from `gh pr view --json number,url` (5 seconds), else it is `null` with `prSource` `unresolved`. A `gh pr create` that pushes the branch itself yields a `push` and a `pr-create` record; both are kept.
- The command text and the tool output are never recorded. Session ids that are not plain file-name characters are treated as absent.
