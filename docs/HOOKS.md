# Hook reference

Every wired `PreToolUse` guard reports a tool event it cannot classify with a fixed warning instead of going quiet (issue #808); see [Event shape coverage](#event-shape-coverage) at the end.

Every hook Kherep wires, one row each. A hook is wired when one of these sources runs it:

- the Claude settings templates, `claude/settings.user.json` and `claude/settings.project.json`: the hooks under `hooks/`, which start through the hook runtime entry, and the Control Plane hooks, which run through the stable entry point `kherep/control-plane/claude-control-plane-hook.mts`;
- the Codex hook block that `codex/lib/parity-config.mts` renders for the installer;
- the Git hooks that `bootstrap/manifest/files.txt` installs into the bound `core.hooksPath` directory.

`bootstrap/hooks-reference.test.mts` reads those sources and fails when a wired hook has no row here or more than one, when a row names a hook nothing wires, or when a row's cells break the vocabulary below. Add a row in the same change that wires a hook.

**Runtime** names where the hook runs: `Claude`, `Codex`, `Git`, and `Control Plane` for the hooks under `modules/control-plane/node/` or the entry point that runs them. **Event** is the hook event and matcher; for Codex it also names the adapter phase or the dispatcher. **Kind** is one of:

- `blocking guard`: denies the tool call, commit or dispatch when its rule is broken.
- `asks operator`: asks the operator to confirm the call.
- `watcher (warns)`: reports a finding without blocking; the integrity hooks also repair what they find.
- `recorder`: writes a record and never blocks.
- `context`: adds text to the session's context, or wakes it.
- `gate`: stops a turn, or sends a turn or a subagent result back, when a required element is missing; each row says whether it does so only once.

The scripts `claude/hooks/cbm-*` have no row: the Claude template does not wire them. Codex runs its own reminder, `codex-cbm-reminder`.

## Event shape coverage

Each wired `PreToolUse` guard has one row in `claude/hooks/lib/tool-event-contract.mts`: the tools it judges and the `tool_input` key it reads (issue #808). When a guard would allow a call without printing anything and the event does not fit its row, it prints a fixed `[kherep:event-shape:WARN:<guard>:<reason>]` line instead, as notice-only `PreToolUse.additionalContext` and on stderr. The seven reasons are `EVENT_ENVELOPE_INVALID`, `TOOL_NAME_MISSING`, `TOOL_NAME_INVALID`, `TOOL_INPUT_MISSING`, `TOOL_INPUT_INVALID`, `COMMAND_MISSING` (the key the guard reads is absent) and `COMMAND_INVALID` (it holds no string). A warning contains no input value and changes no permission decision: every deny, ask and exit code stays as it was, and a missing `tool_name` is warned about, not denied. An event for another tool, a valid empty command and absent optional metadata stay silent. The guards do not guess renamed keys or widen their matchers.

On Claude the dispatcher joins the warning with the other guards' output. On Codex the adapter classifies the native event before its normalization for every guard whose row has a Codex shape, so a renamed field cannot hide behind the normalized form; as in Stage 1, that adapter warning also rides along when the same call is denied, with the decision and its reason unchanged. The shell dispatcher admits from each of its four slots only that slot's own exact warning document, and any other notice from a slot is still a deny. A guard without a Codex shape that Codex runs through the adapter prints the warning itself. `claude/hooks/tool-event-contract.test.mts` and `codex/hooks/tool-event-contract.test.mts` prove, per guard, that a known-bad event still blocks, that dropping or renaming `tool_name` or `tool_input` or renaming the input key gives a block or the warning and never silence, and that another tool's event stays silent. `bootstrap/hooks-reference.test.mts` pins this table to the contract.

| Guard | Claude | Codex |
|---|---|---|
| `commit-guard` | guard warns | adapter warns (native event) |
| `deploy-guard` | guard warns | adapter warns (native event) |
| `main-checkout-guard` | guard warns | adapter warns (native event) |
| `module-label-guard` | guard warns | adapter warns (native event) |
| `privacy-boundary-guard` | guard warns | adapter warns (native event) |
| `secret-output-guard` | guard warns | not wired |
| `playwright-file-guard` | guard warns | guard warns |
| `dispatch-contract-guard` | guard warns | not wired |
| `atlassian-destructive-guard` | guard warns | guard warns |
| `obs-handback-gate` | guard warns | not wired |
| `codex-dispatch-contract-guard` | not wired | denies |
| `mcp-intent-hook` | not wired | unproven |

`adapter warns (native event)` covers Codex's own `codex-privacy-boundary-guard` under the `privacy-boundary-guard` row. `codex-dispatch-contract-guard` denies a missing or non-string `tool_name` itself. `mcp-intent-hook` has no row: nothing proves that a renamed field reaches a deny or a warning, and that stays documented rather than tested for now.

What stays unproven:

- **The matcher blind spot.** A runtime starts a guard only when the tool name matches its group's matcher. If a runtime renames a tool, for example `Bash`, every guard behind that matcher never runs, so no warning can appear; the guards that see all tools (`privacy-boundary-guard`, `secret-output-guard`, `playwright-file-guard` on Claude) classify the new name as another tool and print no warning; `secret-output-guard` and `playwright-file-guard` still apply their rule, because they do not read the tool name. A second shell tool that no matcher names is the same blind spot: Claude Code for Windows runs shell commands through `PowerShell` as well as `Bash`, and until issue #808 only a `Bash` group started `commit-guard` and `deploy-guard`, which the guard canary measured on Windows as `ALLOWED`. Only a call through the real runtime can show it: the [guard canary](#guard-canary) below does that for `commit-guard`.
- **Native invocation and presentation.** These are source and isolated-install tests with synthetic events; whether a runtime shows the warning to the model or the operator is UNKNOWN.
- **No durable record.** A warning lives only in that call's output; nothing collects it yet.

## Guard canary

`bootstrap/guard-canary.mts` checks that a guard still blocks a call that comes from a real runtime turn (issue #808, stage 2b). Only the operator starts it. No hook, schedule or CI job runs the live mode, because one live run spends model tokens on each runtime it covers. Run it after an install, an upgrade or a CLI update.

- **Live mode** (`--runtime claude|codex|both`, default `both`). For each runtime, the canary creates a throwaway git repository in the temporary directory and runs one headless turn there: `claude -p` with `Bash(git commit *)` allowed and no permission prompts, or `codex exec` in the `workspace-write` sandbox with that repository's `.git` added as a writable root. Hooks stay on. The prompt asks for a control commit `kherep-canary-control <nonce>` and then a commit whose message contains an em dash, which `commit-guard` denies. The verdict comes from the repository's `git log`, plus the raw runtime output for the deny. Each run has a time limit (`--timeout`, 300 s by default), and the repository is removed afterwards. The runtime is looked up on `PATH` only.
- **Synthetic mode** (`--synthetic [--checkout <repo>]`). Pipes the same known-bad event through the installed Claude dispatcher command from `<home>/settings.json` (the `PreToolUse` group that matches `Bash` and runs `commit-guard`). With `--checkout`, it also pipes the event through a copy of that checkout's `claude/hooks` dispatcher. No model is called. This mode covers the Claude dispatcher only.

| Verdict | Exit | Meaning |
|---|---|---|
| `DENIED` | 0 | Live: the control commit exists, the bad commit does not, and the raw output contains the guard's fixed deny text `commit message contains an em dash (U+2014)`. Synthetic: the dispatcher printed a deny whose reason contains that text, or exited 2 with it on stderr. |
| `ALLOWED` | 1 | Live: the bad commit is in `git log`. Synthetic: the dispatcher allowed the event. This is a failure: the guard did not block the call. |
| `INCONCLUSIVE` | 2 | Anything else: CLI missing or unusable, no control commit (for example an auth failure or a refused prompt), a rewritten bad commit, no deny text, an unreadable `git log`, a timeout, missing wiring. Missing evidence never counts as a pass. |

When results are combined, any `ALLOWED` gives exit 1. Otherwise any `INCONCLUSIVE` gives exit 2, and only all `DENIED` gives exit 0. The report `<home>/.cache/guard-canary/last-report.json` (`<home>` is `--home`, else `CLAUDE_CONFIG_DIR`, else `~/.claude`) records the mode, the timestamp, and per runtime the verdict, the reason and the `--version` line. It never contains the nonce, the prompt, the output or a path.

The canary proves one guard (`commit-guard`) behind the matcher of the shell tool the runtime chose for that turn (`Bash` or, on Windows, `PowerShell` on Claude; the shell group on Codex) for the runtime versions it ran. The synthetic mode sends a `Bash` event only, so it does not cover the `PowerShell` group. It says nothing about the other guards, and it does not show whether a runtime presents the deny to the operator.
